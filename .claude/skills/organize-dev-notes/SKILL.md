# 開發紀錄 Markdown 整理任務

請閱讀指定的 Markdown 開發紀錄，將零散、重複、順序混亂的內容整理成一份結構完整、語意清晰、可長期維護的技術文件。

## 1. 整理目標

* 合併重複內容，將相同主題集中整理。
* 修正口語化、不完整或語意不清的句子。
* 重新建立開發流程、問題與技術決策的關係。
* 區分已完成、進行中、待辦與待確認事項。
* 保留重要程式碼、指令、錯誤訊息及技術細節。

## 2. 整理原則

* 不得虛構或擅自補充原始文件沒有的資訊。
* 不得改變程式行為、技術決策、API、檔名、路徑或參數。
* 無法確認的內容標記為 `待確認`。
* 前後矛盾的資訊必須同時保留，並列入「待確認事項」。
* 過時或失敗的方案移至「已排除方案」，不要直接刪除。
* 可刪除無助於理解的操作流水帳。
* 全文使用正體中文，技術名詞可保留英文。

## 3. 建議文件結構

請依實際內容調整，不要建立空章節。

```markdown
# 文件標題

## 1. 文件目的
## 2. 背景與需求
## 3. 系統現況
## 4. 整體流程
## 5. 開發內容
## 6. 問題與處理紀錄
## 7. 技術決策
## 8. 已排除方案
## 9. 測試與驗證
## 10. 已知限制與風險
## 11. 待辦事項
## 12. 待確認事項
```

問題紀錄盡量使用以下結構：

```text
問題現象
→ 影響範圍
→ 原因
→ 解決方案
→ 驗證結果
→ 目前狀態
→ 下一步
```

## 4. 格式要求

* 程式碼與指令使用正確語言的 fenced code block。
* 過長 Log 只保留關鍵錯誤與必要上下文。
* 不要重複貼出相同程式碼。
* 比較資訊可使用 Markdown 表格。
* 複雜資料流可使用 Mermaid。
* 待辦事項使用核取方塊：

```markdown
- [ ] 待完成事項
- [ ] 待驗證事項
```

## 5. 執行流程

第一階段只進行分析，不要修改任何檔案。請先回報：

1. 文件主要目的與內容摘要。
2. 建議的文件標題與章節結構。
3. 發現的重複、矛盾及缺失資訊。
4. 預計合併、保留、簡化的內容。
5. 建議的輸出檔名。

等待我確認後，再執行第二階段：

* 整理完整文件。
* 輸出為新的 Markdown 檔案。
* 不得覆蓋原始檔案。
* 建議命名為 `原始檔名_cleaned.md`。

完成後回報：

```markdown
## 整理結果

- 原始檔案：
- 輸出檔案：
- 合併的內容：
- 發現的矛盾：
- 待確認事項：
- 簡化或移除的內容：
```

## 6. 輸出前檢查

確認以下事項：

* 標題層級與內容順序正確。
* 沒有不必要的重複內容。
* 技術名詞前後一致。
* 問題、原因及解決方案正確對應。
* 已完成與待辦事項清楚區分。
* 程式碼、指令與路徑保持原意。
* 沒有加入未經證實的推測。
* 新讀者能理解目前狀態與下一步。

## 7. 任務輸入

需要整理的檔案：

```text

```

文件用途：

```text
<開發維護／問題排查／技術決策／專案交接>
```

預期讀者：

```text
<開發者／維運人員／專案主管／AI Coding Agent>
```
