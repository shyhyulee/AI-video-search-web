# 專題發表投影片 — 說明與數據出處

> **類型**：簡報素材｜**狀態**：維護中，對應 docs/ 底下的投影片 HTML
> 分類說明與完整索引見 [`README.md`](README.md)。

## 1. 這份文件的用途

`docs/專題發表投影片.html` 是資策會結訓專題發表用的十頁簡報，對象是**到場的廠商與招募方**，不是技術交接文件。這份說明負責三件事：

1. 每一頁要講什麼、為什麼這樣排。
2. **投影片上每一個數字的出處**（第 4 節）——發表現場被追問時可以當場查到來源，這是這份文件最主要的價值。
3. 目前還沒處理完的事項（第 6 節）。

跟既有文件的分工：

| 文件 | 負責的問題 |
|---|---|
| 這份 | 對外簡報怎麼講、數字從哪來 |
| [`00-overview.md`](00-overview.md) | 專案全貌與系統現況 |
| [`02-technical-decisions.md`](02-technical-decisions.md) | 每個技術決策的背景與實測數據 |
| [`03-testing-and-evaluation.md`](03-testing-and-evaluation.md) | 評測方法與 baseline 演進 |
| [`04-known-limitations-and-open-items.md`](04-known-limitations-and-open-items.md) | 已知限制與待辦 |
| [`06-search-query-logic.md`](06-search-query-logic.md) | 一句查詢實際被怎麼處理 |

## 2. 檔案與操作

### 2.1 兩個版本

| 檔案 | 頁數 | 內容 | 適用場合 |
|---|---:|---|---|
| `docs/專題發表投影片.html` | 10 | 完整版 | 正式發表、有充足時間講解 |
| `docs/專題發表投影片_精簡版.html` | 5 | 完整版的第 1／2／4／8／10 頁 | 攤位快講、時間被壓縮時 |

精簡版保留：封面、問題、系統架構、產品、邊界與下一步。省略的是 Demo（P3）、雙通道與 RRF（P5）、關鍵決策（P6）、量化成效（P7）、成本與工程品質（P9）。

**精簡版為了能獨立閱讀，做了三處必要補寫**（因為被省略的頁面原本負責交代這些名詞）：

| 位置 | 補寫內容 |
|---|---|
| P3 技術棧 | 新增一列「檢索」：語意向量與關鍵字 BM25 雙通道各自評分，再依名次以 RRF 融合排序 |
| P4 透明度段落 | 「融合分數」後補上括號說明「雙通道名次融合後的實際排序依據」 |
| P5 前兩項限制 | 「關鍵字軌／語意軌」改寫成「關鍵字比對層／語意層」，不再依賴 P5 建立的詞彙 |

除此之外，五頁的文字與數字與完整版完全相同。精簡版的 CSS 與完整版一字不差（含這 5 頁沒用到的規則），因此要把任何一頁從完整版貼回精簡版都不必補樣式。

### 2.2 共同操作

| 項目 | 內容 |
|---|---|
| 格式 | 單一 HTML，樣式與腳本全部內嵌，無建置步驟 |
| 外部相依 | 僅 Google Fonts（Noto Serif TC／Noto Sans TC／JetBrains Mono），離線會退回微軟正黑體，版面不壞 |
| 翻頁 | 方向鍵、空白鍵、PageUp／PageDown、Home／End，或點右側圓點 |
| 存 PDF | Ctrl+P → 另存為 PDF → **務必勾選「背景圖形」**。已設定 A4 橫向、一頁一張投影片 |
| 版面 | 16:9，字級用 `cqw`（container query 單位）綁定投影片寬度，縮放不會跑版 |

視窗寬度小於 700px 時自動放棄 16:9 改為自然高度，方便手機預覽；列印時不受此影響。

## 3. 十頁架構

| # | 頁面 | 這頁要讓對方記得的一件事 |
|---:|---|---|
| 01 | 封面 | 「用一句話，跳到影片的那一秒」＋ 四個實績數字 |
| 02 | 問題 | 影片是企業裡搜不到內容的黑盒子；三個產業場景 |
| 03 | **實際執行結果** | 真實查詢重現：8 個片段、3.0 秒、秒級定位 |
| 04 | 系統架構 | 七步分析 Pipeline ＋ 技術棧 ＋ 單向依賴分層 |
| 05 | **技術核心** | 雙通道檢索與 RRF 融合：看名次不看分數 |
| 06 | 關鍵決策 | 三個決策各附實測前後數字 ＋ 無答案訊號探索表 |
| 07 | 量化成效 | Golden Set 三版本指標對照 |
| 08 | 產品 | 五頁籤動線；AI對話的責任切分；刻意保留的透明度 |
| 09 | 工程 | 成本可觀測性 ＋ 測試與架構品質 |
| 10 | 邊界與下一步 | 誠實的限制清單 ＋ Roadmap ＋ 聯絡方式 |

**編排邏輯**：03 頁刻意緊接在問題之後——先讓對方看到「東西真的會動」，再進技術細節，避免前四頁都在講架構卻還沒證明成果。10 頁主動講限制是刻意的：對技術背景的廠商，一份誠實的限制清單比多列兩個功能更有說服力。

## 5. 設計決策

### 5.1 配色沿用產品自己的 token

投影片的底色與強調色直接取自 `frontend/src/index.css`，讓簡報與實際產品是同一套視覺語言：

| 用途 | 值 | 對應 app token |
|---|---|---|
| 頁面底色 | `#F8F3ED` | `--color-app-bg` |
| 卡片 | `#FFFDF9` | `--color-card` |
| 深一階檯面 | `#F1E4D5` | `--color-sand` |
| 強調區塊底 | `#F7E4DC` | `--color-primary-soft` |

### 5.2 強調色分成文字階與色塊階

app 的原始強調色是為「白字配實心背景」調的，直接放到米色底上當文字用對比不足（例如 `#DC9A3C` 對 `#F8F3ED` 只有約 2.1:1，投影會看不清）。因此每個強調色拆成兩階：

| 色 | 文字階 | 色塊階 | 用途 |
|---|---|---|---|
| 赭紅 | `#A8492F` | `#C4674B` | 主強調、頁碼、標籤 |
| 琥珀 | `#8A5A12` | `#DC9A3C` | **字幕**模態 |
| 灰綠 | `#52634A` | `#8FA383` | **OCR** 模態、正向數字 |

四組文字色對米色底皆通過 WCAG AA（約 5.3–5.9:1）。

### 5.3 三模態綁定固定顏色

字幕＝琥珀、畫面＝赭紅、OCR＝灰綠，全篇一致。P3 的長條圖、P5 的雙軌卡片邊框、P3 的引文左框線都遵守同一組對應，讓「顏色」本身承載資訊，而不只是裝飾。

### 5.4 單一視覺世界，不隨系統主題翻轉

刻意不做深／淺色雙主題。投影場合若隨觀眾裝置或作業系統設定變色會失控，所有顏色明確指定。

## 6. 待處理事項

- [ ] **確認每支影片預算上限的實際值**（`BUDGET_USD`）。[`02`](02-technical-decisions.md) 記載調高到 US$0.30，[`04`](04-known-limitations-and-open-items.md) §1 寫「目前 US$0.80」，兩者不一致。確認後補進投影片 P9，並順手修正較舊那份文件。
- [ ] **決定字型是否內嵌**。目前走 Google Fonts CDN，發表現場若無網路會退回微軟正黑體（版面不壞，但質感下降）。若場地網路不可靠，可改為將三套字型子集化後以 data URI 內嵌。
- [ ] **P1 統計數字的時效性**。14 支／828 片段／US$1.29 是 2026-08-26 的快照，之後若再分析新影片就會與畫面不符。發表前重新看一次 Header 統計卡並同步。
- [ ] **考慮是否加一頁商業應用場景**。目前十頁偏技術深度，若現場廠商以招募為主，補一頁「可落地產業與應用想像」會更完整。

## 7. 怎麼修改

樣式集中在檔案開頭 `:root` 的 CSS 變數區，改色只需要動那一段。每頁投影片是一個 `<section class="slide" id="sN">`，內容直接改 HTML 文字即可，右側導覽圓點由腳本依實際頁數自動生成，增減頁面不需要另外調整。

新增一頁時記得同步該頁 `<footer class="foot">` 裡的頁碼與總頁數文字（目前是手寫的 `NN / 10`）。
