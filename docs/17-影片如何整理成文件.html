技術詳解

一部影片，怎麼變成一份文件

從影片檔進來，到畫面上出現一份有章節、有步驟、點得動時間戳的文件，中間發生了什麼事。先看四個階段的大架構，再逐一拆開每個環節用了什麼方法、為什麼這樣做。

Part 0

一頁看完

一句話：把整支影片先拆成一段一段的「片段」，每段記下畫面、聲音、螢幕上的字，再把這些片段依時間順序攤成一長串文字餵給語言模型，要求它回傳一份有固定格式的文件。

STAGE 1 產生片段 影片 → 片段。切場景、聽字幕、看畫面、認螢幕文字。
analyzer.py Phase A–E
STAGE 2 攤成素材 片段 → 一長串逐行文字，順便把雜訊丟掉。
segment_material.py
STAGE 3 整理成文件 素材 → 結構化文件。單次 LLM 呼叫，回傳固定形狀的資料。
document.py
STAGE 4 落地與呈現 存回資料庫 → 前端畫成可點的章節與步驟。
db → api → React

深色兩格是「文件線」真正專屬的部分，也是這份文件的重點；第 1 階段是整個分析 pipeline 共用的，第 4 階段是一般的資料落地與前端渲染。

資料在管線裡的形狀變化

影片檔
一支 MP4，長度上限 1 小時（MAX_DURATION_SEC）。
↓　場景切分 ＋ 語音轉錄 ＋ 畫面分析
segments 表
數十到數百筆片段，每筆帶起訖秒數與三個文字欄位：visual_description（畫面描述）、transcript（字幕）、ocr_text（畫面上的文字）。
↓　build_material()　攤平 ＋ 過濾雜訊
一個字串
逐行素材，一行一個片段：
[03:18｜198 秒] 畫面：…；字幕：…；畫面文字：…
↓　generate_document()　單次 LLM 呼叫（structured output）
VideoDocument
一份結構化文件：文件類型、標題、概述、章節[]（各含步驟[]，每步帶秒數）、影片未涵蓋事項[]。
↓　存進 videos 表（整包 JSON ＋ 兩個索引欄位）
畫面
可讀的文件：章節標題、編號步驟、每步左側一個可點的時間戳，點下去影片就跳到那一秒。

為什麼要有這一層？分析完的影片，系統手上其實握著整支的畫面描述、字幕與畫面文字，但使用者拿得到的只有兩種東西：一段 100～200 字的摘要（太粗），或是搜尋命中的單一片段（太細）。中間那層——「這支工廠影片的生產流程到底是哪幾步」——沒有人做。這份文件功能補的就是這一層。

每個階段的輸入、輸出與負責的檔案如下。第 2、3 階段是文件線專屬，第 1、4 階段與其他功能共用。

自動那條路的核心設計：文件優先，摘要當退路

Phase F 原本只產摘要。改成先整理文件、摘要當成文件的副產品之後，省掉一次 LLM 呼叫——因為文件裡的「概述」欄位本來就是照摘要的規格寫的，使用者按「整理成文件」時本來也會覆蓋掉摘要欄位。既然我們早就認定文件的概述才是正本，就沒有理由先花錢產一份注定被覆蓋的摘要。

但退路不能省。videos.summary 不只是給人看的欄位——搜尋的影片層級篩選與影片庫的主題分類都在讀它。文件整理失敗就整支影片沒有摘要的話，那支影片會在搜尋端被降權，比「文件沒整理出來」嚴重得多。所以文件失敗時會退回原本的摘要產生器；兩條都失敗才放棄，而且只記 log，不讓已經成功的分析結果被判定為失敗。

第一順位
整理文件 → 同時得到文件與摘要 理想
↓　失敗（refusal／輸出被截斷／API 錯誤）
退路
只產摘要 → 沒有文件，但搜尋不受影響 可接受
↓　再失敗
放棄
只記 log → 影片仍然標記為分析完成，片段與搜尋都正常 降級
技術細節：預算隔離與平行化

Phase E（本地 OCR）與 Phase F（整理文件）互不依賴——F 只讀 Phase D 寫入的 segments，不碰 Phase E 寫的 ocr_events——所以同時起跑縮短耗時。兩者各拿一個 ctx.budget_branch()，都以「進入這個函式那一刻」的金額當預算判斷基準，互相看不到對方的花費。

代價是極端情況下兩者合計可能讓總花費比 BUDGET_USD = 0.80 多出一點點，這是刻意接受的取捨，用 budget_branch() 把它變成明講的機制而不是靠傳參數傳出來的副作用。

已知取捨：Phase F 的耗時從幾秒變成數十秒（輸出 token 比摘要多一個量級），但因為與本地 OCR 平行跑，多出來的時間多半被吸收掉。每支影片多花約 US$0.002，相對 US$0.80 的預算可忽略，沒有調整預算上限。

Part 2

逐環節拆解

以下每個環節固定分成四段：輸入是什麼、做了什麼、為什麼這樣做、以及支撐這個決定的實測數字。專案裡幾乎每一條規則都是被真實資料逼出來的，不是先驗設計。

3.1片段哪裡來（背景）

輸入：一支影片檔。輸出：segments 表裡數十到數百筆片段。

文件功能其實不參與這個階段——它只是讀者。但要理解後面的每一個決定，得先知道片段長什麼樣子：每一筆片段有起訖秒數，加上三個各自可能為空的文字欄位。

欄位怎麼來的全庫覆蓋率可靠度
visual_description
畫面描述		 VLM 逐場景抽幀「看圖說話」（gpt-4o-mini） 1,155 / 1,156 最穩定，覆蓋率 99.9% 的骨幹
transcript
字幕		 整支影片音訊轉文字（whisper-1） 1,006 / 1,156 會整段壞掉：純音樂或無人聲時會生出幻覺文字
ocr_text
畫面文字		 VLM 同一次呼叫順便讀；本地 EasyOCR 補漏 1,076 / 1,156 對流程類影片價值極高，但混著頻道浮水印

數字來自全庫 23 支影片、1,156 個片段的實測分布。片段長度被正規化到 8～12 秒（太短的合併、太長的均分），所以片段密度的結構上限是每分鐘 7.5 個，不會因為影片剪得很快就失控。

這一階段（場景切分演算法、Whisper 的兩種幻覺過濾模式、VLM 條件式多幀取樣、EasyOCR 雙引擎、向量建立）的完整拆解在另一份文件：16-技術詳解：五個技術層與分析流程。這裡不重複。

3.2攤成素材 重點

輸入：片段清單。輸出：一個長字串，一行一個片段。負責：segment_material.build_material()。

語言模型吃的是純文字，所以要把資料庫裡的片段攤平。這聽起來像是無聊的格式轉換，實際上這裡的每一個決定都直接影響最後文件的品質——而且是被踩過坑之後才修對的。

# 素材長這樣，一行一個片段
[00:16｜16 秒] 畫面：機械手臂正在將車身骨架移入焊接站；畫面文字：BODY IN WHITE
[00:24｜24 秒] 畫面：焊接火花四濺，多支機械臂同時作業；畫面文字：SPOT WELDING · STAGE 3
[00:36｜36 秒] 畫面：輸送帶將車身送往下一站

決定一：時間戳同時給「分:秒」與「總秒數」

做了什麼：每行開頭寫成 [03:18｜198 秒]，兩種格式都給。

為什麼：文件的資料結構裡，每個步驟的時間欄位叫 timestamp_sec——要的是秒數。但素材原本只給 [MM:SS]，等於逼模型自己心算換算，而它經常不換算，直接把 [03:18] 的 18 抄進去。

結果就是兩種看起來完全不同、實際同源的症狀：步驟時間戳全部塌在影片前 60 秒內，或是寫出超過影片長度的時間點（一支 18:33 的影片寫出 22:56 的步驟）。

這件事一度被誤判成「模型幻覺」。當時的結論是「模型講得出時間戳也可能是編造的」，還為此在前端加了防護。追下去才發現根因是我們自己的素材格式與資料結構不一致。前端防護留著當安全網，但它從主要對策降級成保險。

實測數字：只改時間戳格式，重跑 9 支文件

驗證方式是三次單變數實驗（每次約 US$0.002，唯讀不寫庫）：實驗一先濾掉幻覺字幕 → 步驟數變多，但時間戳仍全塌在 00:56 內（證明兩個成因獨立）；實驗二只改時間戳格式 → 時間戳散到 08:42；實驗三在另外兩支影片重複 → 一致。

指標修正前 → 後
超出影片長度的步驟4 → 0（9 支全清）
時間戳涵蓋率（最差兩支）BMW 5%→80%、Python 18%→93%
涵蓋率略降的龍隊 31%→25%、線性代數 74%→57%
步驟數有增有減（技嘉 19→12、Python 7→14）

沒有全面改善，也不假裝有：步驟數與涵蓋率有增有減，單次重跑分不出訊號與雜訊。唯一乾淨清掉的是「超出影片長度」。

決定二：整欄都是幻覺的字幕，整欄丟掉

做了什麼：先統計「最常出現的那一句佔全部字幕的比例」，超過 40% 就整支影片的字幕欄全部不用。

為什麼：純環境音或純配樂的影片，語音辨識會整支輸出同一句罐頭台詞。某支 BMW 工廠影片 97 句字幕裡，70 句一字不差是 Thank you for watching.（72%），算上變體共 95 句（98%）。字幕欄一旦變成噪音，它還會把真正有訊號的欄位稀釋掉——那支影片的畫面文字欄其實有 67 句各自不同的製程旁白，但模型被字幕干擾，只寫出 7 個步驟。

走過的冤枉路：專案早就有一個逐片段的幻覺偵測（判斷「這一段像不像人聲」），一度以為文件端接上它就好。拿全庫量過才發現工具選錯了——它在 BMW 抓到 76/97，但同樣整欄是幻覺的另一支只抓到 2/108；反過來真實講課的那支卻有 16 段被誤標。逐片段的信心分數看的是「像不像人聲」，而幻覺字幕的特徵是「整支影片一直重複同一句」——後者只有把整支影片放在一起看才看得出來。

實測數字：門檻 0.4 是怎麼定的

全庫 23 支影片的「單一句佔比」分布乾淨可分：

類別單一句佔比
未觸發（真實語音／混合）1% ～ 26%
觸發（整欄幻覺）65% ～ 79%

中間 26%～65% 是空的，門檻放哪裡都一樣。另外設了樣本下限 _MIN_SAMPLES_FOR_JUNK_CHECK = 8：整支只有 3 句字幕的影片，其中 2 句剛好一樣就湊出 67%，那是樣本雜訊不是幻覺訊號，寧可漏也不要誤殺。

驗收先做不花錢的那半：23 支全部跑一次判定，比對事前從資料分布標好的預期，22/23 相符，唯一不符的正是那支只有 3 句字幕的（刻意不判定）。之後才花 US$0.0019 重產 BMW 的文件：步驟數 7 → 12、時間戳範圍 16s～1041s（片長 1063s）、涵蓋率 81% → 98%、素材長度 -26%。

決定三：浮水印 OCR 只丟那個字串，不丟整欄

做了什麼：畫面文字欄裡，出現比例超過 15% 的字串本身被移除，同欄其他內容照留。

為什麼：處理方式刻意與字幕相反。重複的畫面文字通常是頻道浮水印（FRAME、CPBL TV、SPORTS HD），但同一欄的其他內容正是主要訊號——BMW 那支的製程旁白全在這一欄，整欄丟掉等於把僅有的內容也丟了。字幕則不同：一句佔到 72% 時，剩下的 28% 實測也是同一類垃圾，留著沒有意義。

實測：門檻 0.15 抓到的全是浮水印（佔比 21%～47%），真實內容的最高佔比只有 12%，零誤殺。

決定四：把欄位內的換行壓成空白

做了什麼：每個欄位的內部換行壓成單一空白。

為什麼：prompt 開頭就宣告「每行是一個片段」，但畫面文字與字幕本身可能帶換行——那些被撐出來的行沒有時間戳前綴，模型無從得知它們屬於哪個片段。實測每一支影片都有這個問題，比例 28%～88%（某支線性代數影片是 461/526 行沒有時間戳）。壓成空白之後，那句宣告才是真的。

決定五：文件帶畫面文字，摘要不帶

這是這個模組唯一的開關 include_ocr。畫面文字覆蓋率 93%，對流程類影片特別有價值，但摘要用不到、文件用得到。

壽司那支證明它是決定性的：文件裡的「上方保留 3 公分」「靜置 10 分鐘讓壽司釋放」逐字來自畫面上的字卡。那支影片字幕全壞（純音樂觸發的外語幻覺），畫面描述只講得出「捲起來」——不帶畫面文字的話，會產出一份沒有任何份量與時間的空洞食譜。

技術細節：為什麼摘要與文件共用同一個模組，但截斷各留各的

摘要與文件本來各有一份幾乎相同的素材組裝實作，連時間格式化函式都是逐字重複的。兩者的 prompt 目的不同，但「素材長什麼樣子」是同一個決定——時間戳格式、欄位標籤、分隔符號、空片段要不要略過——改其中一邊而忘了另一邊，兩個功能餵給模型的素材就會悄悄長得不一樣。所以抽成共用模組（動手前拿全庫 1,156 個片段比對過新舊輸出逐字元相同）。

但截斷刻意留在各自的呼叫端：摘要只取前 200 段（控制 prompt 長度），文件完全不截斷。理由見 3.3 的「不做硬截斷」。這是兩邊各自的決定，留在呼叫端才看得見。

另外，畫面文字欄裡有 21 個片段的值是字面字串 "null"（VLM 回傳的字串沒被正規化成 NULL）。組素材時會濾掉，但資料庫裡的髒資料沒有回填修正，其他讀這個欄位的地方仍會吃到。

3.3交給模型 重點

輸入：素材字串 ＋ 影片標題。輸出：一份 VideoDocument。負責：document.generate_document()。

整條管線只有一次 LLM 呼叫（gpt-4o-mini）。關鍵在於它不是「請幫我寫一份文件」這種開放式請求，而是用 structured output 事先把答案的形狀釘死。

為什麼是 structured output，不是讓模型吐 Markdown

讓模型吐 Markdownstructured output 採用
前端渲染要引進 Markdown 函式庫（新依賴），或用純文字硬撐出沒有階層的一坨字直接用既有元件排版，零新依賴
時間戳藏在文字裡，要回頭用正則解析獨立的數字欄位，直接交給播放器
形狀保證沒有；模型高興怎麼寫就怎麼寫由資料結構定義強制，缺欄位就是錯誤

回傳的資料形狀

VideoDocument
├─ doc_type    # 四選一：sop / tutorial / lecture_notes / content_log
├─ title       # 文件標題（不必照抄影片標題）
├─ overview    # 3~5 句概述 —— 一稿兩用，同時當成影片摘要
├─ sections[]  # 章節
│   ├─ heading
│   └─ steps[]
│       ├─ timestamp_sec   # 秒數，必填 ← 防幻覺的主要手段

└─ uncovered[] # 素材裡沒交代、讀者要自己補的事

模型自己判斷文件類型

不是使用者選，也不是規則判斷，而是模型看完素材自己歸類：

類型什麼時候選產出長相
sop　流程 SOP包含可依序重現的作業流程（產線、製程、操作程序）生產流程 SOP
tutorial　教學步驟教別人做出某個成品（烹飪、手作、DIY）教學步驟
lecture_notes　課堂筆記講解知識或概念課堂筆記
content_log　內容紀錄最後的退路：前三類都不成立時（球賽、排行榜、風景）依時間軸的內容紀錄

第一版會被敘事形式騙走。一支主機板工廠影片被判成 content_log 而不是 sop——內容其實完全正確（章節就叫「主板生產線」，步驟是塗矽膏 → 貼片機 → 測試 → 包裝），只有型別錯了。原因是那支用第一人稱參觀敘事開場（「我是翼王，這次來帶大家參觀」），模型看形式而不是看內容。

修法是在 prompt 明講：判斷時看內容，不要看敘事形式；第一人稱參觀／vlog／開箱只要交代了可重現的步驟就選 sop／tutorial。修完四種類型全部判對，而且球賽那支沒有被過度矯正（仍是 content_log，沒有硬掰出打擊 SOP）。

三條寫進 prompt 的硬規則

這三條都來自實測資料，不是想像出來的。規劃時查了真實資料庫，發現使用者舉的兩個範例素材結構正好相反：

影片流程知識在哪一欄另一個模態的狀況
主機板工廠字幕（「第一步首先就是往已經生產好的 PCB 塗矽膏…」）畫面描述是雜訊（「畫面顯示一面金屬光滑的牆面」）
不用竹簾捲壽司畫面描述 ＋ 畫面文字字幕是純音樂上的外語幻覺
  1. 每個步驟必須對得上素材裡的某個時間點，直接填方括號裡的秒數。素材裡沒有的一律不准寫——寧可少寫，不要補完。判斷得出「這裡應該還有一步但素材沒交代」的，寫進 uncovered。
    這是防幻覺的主要手段：講不出「這是影片第幾秒的內容」的步驟，通常就是模型自己補出來的。
  2. 字幕與畫面描述矛盾時以畫面描述為準，看不懂的片段直接略過。
    因為畫面是覆蓋率 99.9% 的骨幹，字幕才是會整段壞掉的那個。
  3. 不適合就不要硬掰。判斷成 content_log 時就老實做時間軸紀錄，不要為了湊出流程而發明步驟。

不做硬截斷

摘要那邊只取前 200 段來控制 prompt 長度，文件這邊刻意不抄：摘要截掉尾段只是摘要不完整，SOP 截掉尾段會默默少掉最後幾個製程步驟——使用者拿到一份看起來完整、實際缺了結尾的流程文件，比直接失敗更糟。

取而代之的是一個防呆上限：超過 600 段就明確丟錯。那不是截斷，是「這批資料明顯不對勁」的判斷——實測片段密度 5.5～6.2 個/分鐘、分析長度上限 1 小時，正常資料最多約 360 段，永遠碰不到 600。

技術細節：呼叫參數與失敗處理 
response = client.chat.completions.parse(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": prompt}],
    response_format=VideoDocument,
    max_completion_tokens=8000,
)

max_completion_tokens=8000：一份 SOP 可能有 20～30 個步驟，比摘要（600）大一個量級；中文字元常拆成 1~2 個 token，留寬一點，因為被截斷會讓解析結果直接變成 None。

解析失敗（refusal 或輸出被截斷）時直接丟錯，不存空殼進資料庫。專案裡其他 LLM 呼叫遇到這種情況可以退回空字串，但這裡沒有合理的「空文件」可退。

為什麼是同步 REST 而不是開一種新的背景工作類型：單次 LLM 呼叫符合既有的判準（工作佇列只服務分析與下載）。實測 33 個片段的影片端到端 7.5 秒，遠低於規劃時估的 20～40 秒。另外加工作類型有兩個已知地雷：重試邏輯會讓新類型靜靜掉進下載分支，前端也只用影片 ID 比對進行中的工作，同一支影片有兩種工作時會抓錯。

3.4存回資料庫

輸入：VideoDocument。輸出：videos 表上的四個欄位。

欄位存什麼為什麼這樣拆
document_json整包 JSON文件的形狀由 pipeline 的資料結構決定，之後 schema 演進只要動那一個地方，資料庫不用跟著改
document_type文件類型另外抽一欄，讓清單頁不用解析整包 JSON 就知道類型
document_model用哪個模型產的可追溯
summary概述欄位的內容一稿兩用，見下

概述一稿兩用，而且下游比想像中多

文件的 overview 會同時寫進影片的摘要欄位。所以 prompt 特別要求它寫成「這支影片在講什麼」而不是「這份文件涵蓋什麼」，也不准用「本文件」開頭——因為這段文字接下來會流進：

overview
→ videos.summary
↓　被三個地方讀走
搜尋
影片層級篩選：先判斷「哪幾支影片可能有答案」再進片段比對
影片庫
主題分類與庫內搜尋
面板
影片詳細資訊上方那段摘要文字

前端的文件檢視刻意不再顯示 overview——它就是面板上方那段摘要，印兩次等於同一段文字出現兩遍。

技術細節：兩條路的成本語意相反，寫錯會把錢算兩次

這是這個功能最容易踩的坑：

手動整理分析時自動整理
寫入函式db.update_video_document()db.mark_video_analyzed()
cost_usd 語意增量累加
cost_usd = COALESCE(cost_usd,0) + %s		絕對總額
（文件的花費已經透過 ctx.spend() 進去了）

所以自動那條路的文件三欄必須跟著 mark_video_analyzed() 一起寫，不能順手改呼叫 update_video_document()——兩支都呼叫的話，同一次 LLM 呼叫的錢會被算兩次。

三個欄位都用 COALESCE(%s, ...)：重新分析但這次文件整理失敗時，舊文件留著比清空好。

順帶修掉的既有問題：把影片重置回待分析狀態時，原本清了摘要卻沒清文件三欄，留下一份時間戳指向已刪片段的文件。文件只能手動整理時這是少見情況，改成自動整理之後每支重置的影片都會遇到，所以一併清掉。

3.5畫到畫面上

輸入：API 回傳的 VideoDocument。輸出：使用者看到的文件。負責：VideoDocumentView.tsx。

  • 還沒整理過就是 404——這是正常狀態不是錯誤，前端用它決定要顯示「還沒整理」還是文件內容。
  • 章節 → 編號步驟，每步左側一個固定寬度、靠右對齊的時間戳，多個步驟的數字才會排成一直排。
  • 時間戳可點就跳播。點下去切進觀看模式（左播放器、右摘要與文件），右欄的時間戳仍可點，邊看邊跳不用退回清單。
  • content_log 用不同顏色的標籤與真正的流程文件區分，使用者才不會以為系統整理失敗了。
  • 「影片未涵蓋的部分」獨立一區。明講哪些是影片有的、哪些要自己補——這份文件會被當成參考資料看，必須分得出來。

超出影片長度的時間戳，不給點

模型仍有可能寫出對不上影片的時間點。前端的做法是：停用那些連結（刪除線＋灰字＋滑鼠提示），並在文件開頭用一句話講出來——

有 N 個步驟的時間點超出影片長度（06:11），已停用它們的播放連結。這通常代表模型在那幾步上寫出了影片裡沒有的內容，內容本身也請斟酌。

只靠滑鼠提示的話，等於只有已經起疑的人才會發現。而且提示裡明講「內容本身也請斟酌」，因為這是呈現層的緩解，不是修好資料：時間點都編得出來的步驟，內容多半也可疑。

技術細節：2 秒容差與無障礙處理

OUT_OF_RANGE_TOLERANCE_SEC = 2：影片長度欄位是整數（來源 metadata 四捨五入過），真實長度可能多零點幾秒，嚴格比較會把剛好落在片尾的合法步驟誤判成超出。2 秒足夠吸收誤差又不會放過真正的問題——實測 8 支文件裡有問題的 3 支，超出幅度分別是 4 分 23 秒、2 分 52 秒、5 分 38 秒，全是分鐘級的。

可點的時間戳用真正的 <button> 而不是加 onClick 的 <span>：鍵盤 Tab 得到、Enter 觸發、螢幕閱讀器讀得出這是按鈕。無障礙標籤帶上步驟標題，因為實測真實文件會有兩個步驟共用同一個時間戳，只講秒數的話螢幕閱讀器會聽到兩個一模一樣的按鈕名稱。

停用的時間戳也用 disabled 的 <button> 而不是純文字：跟旁邊可點的維持同一種外觀語言，使用者看得出「這裡本來應該可以點」，而不是以為這一步比較不重要。

倒退的時間戳沒有處理——它們是影片裡真實存在的位置，點了會正常播放，只是順序讀起來怪。

已知缺口：失敗只有 log 看得出來。一支影片分析完成卻沒有文件時，介面只說得出「沒能整理出文件」，說不出是模型拒絕、輸出被截斷還是超出預算——要看伺服器 log 才知道，工作紀錄表也沒有記這件事。

§6成本與已知限制

成本：可以視為可忽略

影片片段數整理一份文件的成本
壽司5US$0.00042
主機板工廠33US$0.00141
線性代數65US$0.00263

規劃時估 US$0.005/份，實際便宜 2～12 倍。對照整支影片分析的 US$0.10～0.19，文件整理的成本可以視為可忽略。

已知限制

  • 文件品質沒有任何量化方式。搜尋有固定查詢集可以算指標，文件整理沒有——只能人工看。這代表之後改 prompt 沒有回歸測試可擋，改壞了不會有人發現。
  • 幻覺步驟的風險只被緩解、沒有被消除。緩解手段是「每步必須附時間戳」＋「講不出來的寫進 uncovered」，實測 4 支都沒發現編造的步驟，但那是 4 支的樣本，不是保證。一份看起來很專業但編造的製程文件比沒有更糟。
  • 幻覺字幕的過濾擋不住外語幻覺。純音樂影片產生的外語人名清單（單句各不相同、不會觸發重複率判定）仍會進入向量與關鍵字索引，是搜尋端的既有問題。文件端靠 prompt 規則繞過去了。
  • 文件重新整理直接覆蓋，沒有版本歷史。想比較兩次結果只能自己先複製走。
  • 看不出一支影片的成本裡有多少是文件整理。文件成本併進影片總成本、沒有獨立欄位；改成自動產生之後更難拆。
  • 存量影片不會自動補上文件。自動整理只影響「之後才分析的影片」，先前已分析過的仍要有人去按按鈕。
  • 倒退的時間戳沒有處理。章節依主題分時，時間軸本來就可能互相重疊，真正的亂序只剩章節內的個位數。
