## 1. 文件目的

盤點目前 SQLite 存取層的實際樣貌，提出一版可執行的遷移計畫。第 3 節的決定點已於 2026-08-27 拍板。

**這次遷移的動機**（決定了計畫的重點擺哪）：

1. **專題發表／技術展示**——遷移過程本身要能講，所以每一步都要有可展示的產出（見 §9）。
2. **為之後上 pgvector 鋪路**——這次不換向量欄位型別，但環境與 schema 都先準備好（見 §8）。

不是為了效能或資料量（22 支影片／931 個 segments，SQLite 完全夠用）。這點要誠實寫進報告裡。

## 2. 現況盤點（已確認的事實）

### 2.1 程式碼

| 項目 | 現況 |
|---|---|
| 存取方式 | 標準函式庫 `sqlite3`，手寫 SQL，**沒有 ORM**（無 SQLAlchemy／Alembic） |
| 邊界 | `src/ai_video_search_web/db/` 六個子模組共 1348 行，對外只暴露扁平函式介面 |
| 外洩情況 | `db/` 以外**完全沒有** SQL 或 `sqlite3` import，只有 `tests/test_db.py`、`tests/test_search_pipeline.py` 兩支測試直接寫 SQL |

## 3. 已拍板的決定

| # | 決定點 | 決定 | 理由 |
|---|---|---|---|
| D1 | PostgreSQL 放哪裡 | **Docker（`pgvector/pgvector:pg17`，port `5433`）** | 環境乾淨可重現、`docker-compose.yml` 進版控後整套環境是文件的一部分（對專題發表有利）；直接用 pgvector 官方 image 等於 §8 的 pgvector 路線零額外安裝成本。選 **pg17** 對齊 Windows 端已裝的 PG17，pgAdmin 4 可以直接拿來連。port 用 **5433** 而不是 5432：Windows 那個 PG17 服務是手動啟動的，哪天被 pgAdmin 帶起來就會跟 5432 撞埠，換一個號碼永久免除這類問題。 |
| D2 | 驅動與抽象層 | **`psycopg[binary]` 3 + 維持手寫 SQL**，不引入 SQLAlchemy／Alembic | `db/` 已經是乾淨邊界，函式介面不用動。改 ORM 是另一個獨立專案（重寫 1348 行 + 22 支測試），把兩件事綁在一起會讓「搜尋結果變了」無法歸因。psycopg3 的 `conn.execute()` 用法跟 `sqlite3` 幾乎一樣，`row_factory=dict_row` 之後 `row["x"]`、`row.keys()` 都照舊。 |
| D3 | FTS5 的替代 | **`pg_trgm` GIN 索引 + 自算 IDF 加權分數** | 見 §5，這是全案唯一「行為可能變差」的地方。 |
| D4 | 這次要不要一起上 pgvector | **extension 開起來，但欄位型別這次不換**（`BYTEA` 原樣搬） | 動機 2 是「鋪路」不是「這次就上」。P0 會 `CREATE EXTENSION vector`，schema 也預留位置，但換成 `vector(1024)` 要連帶改 `analyzer.py`／`dense.py`／`embedding.py` 的編解碼路徑，那是獨立的一步，見 §8。混在一起做同樣會讓「搜尋結果變了」無法歸因。 |
| D5 | 時間欄位型別 | **維持 `TEXT`（ISO-8601）** | 所有 dataclass 都宣告 `created_at: str`，`ORDER BY created_at DESC` 對 ISO-8601 字串排序結果正確。改 `timestamptz` 要動 6 個 dataclass、所有 API schema 與前端格式化，收益是「型別正確」，這次不換。 |
| D6 | 切換方式 | **一次性切換，不做 dual-write** | 單機單人 app，可停機。回頭路＝原封不動的 `app.db` 備份 + git branch。 |
| D7 | 舊 `app.db` 處置 | **保留，不刪**（依 CLAUDE.md，刪檔一律先問） | 複製一份到備份路徑，確認 PG 穩定跑一陣子再問你要不要刪。 |

## 4. Schema 對照

### 4.1 型別與語法

| SQLite | PostgreSQL | 影響範圍 |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 6 張表。**原本規劃寫 `ALWAYS`，實作時改成 `BY DEFAULT`**：`ALWAYS` 會擋住 P4 保留原 id 的插入（得額外寫 `OVERRIDING SYSTEM VALUE`），而且 `BY DEFAULT` 更貼近 SQLite `AUTOINCREMENT` 允許顯式 id 的語意 |
| `REAL` | `DOUBLE PRECISION` | `start_sec`／`cost_usd`／`confidence` 等 11 欄 |
| `BLOB` | `BYTEA` | 4 個 embedding 欄位 |
| `TEXT` | `TEXT` | 不變 |
| `?` 佔位符 | `%s` | **全部 SQL**。實際數量 **103 處**（jobs 41／videos 37／ocr_events 14／conversations 8／search_log 3），比規劃時估的「約 40 處」多 |
| `cursor.lastrowid` | `INSERT ... RETURNING id` | 5 處（`insert_video`／`insert_segment`／`insert_ocr_event`／`insert_job`／`insert_conversation`） |
| `MAX(COALESCE(col,'') != '')` | `bool_or(COALESCE(col,'') <> '')` | `modality_flags_by_video()`；SQLite 布林是整數，PG 是真布林型別，`MAX(bool)` 會直接報錯 |
| `IN (?,?,?)` 動態展開 | `= ANY(%s)` 傳 list | `modality_flags_by_video()` |
| `PRAGMA table_info` | 不需要 | 見 §4.2 |
| `sqlite3.Row` | `psycopg.rows.dict_row` | `row["x"]`、`"x" in row.keys()` 用法不變 |

### 4.2 `migrate_columns()` 的處置

`videos.migrate_columns()`／`segments.migrate_columns()` 存在的唯一理由是「既有 SQLite 檔案缺新欄位」。
PostgreSQL 是全新資料庫，`CREATE TABLE` 一次把欄位定義齊全就好——**這兩個函式連同 `_VIDEOS_NEW_COLUMNS`／
`_SEGMENTS_NEW_COLUMNS` 一起刪掉**，`init_db()` 對應的呼叫也移除。

代價：之後要加欄位沒有自動機制。以本專案節奏（一人開發、可停機）可接受，需要時再引入 Alembic。

### 4.3 外鍵

新增 `segments.video_id`、`ocr_events.video_id` 對 `videos(id)` 的 `REFERENCES ... ON DELETE CASCADE`。
既有的顯式 `DELETE` 邏輯（`delete_for_video()` 等）**保留不動**——它們先執行、行為不變，FK 只是把
「孤兒列在物理上不可能存在」變成資料庫保證。

另外兩個看起來像外鍵、但**刻意不加**的欄位（實作時才確認的判斷）：

- **`jobs.video_id`**：download job 建立時影片還不存在（下載完才由 `set_job_video_id()` 回填），
  加外鍵會擋住這個正常流程；而且 jobs 是歷史紀錄，影片被刪掉之後那筆工作紀錄仍然應該留著——
  `ON DELETE CASCADE` 會連歷史一起刪、`SET NULL` 會失去關聯，兩者都改變既有行為。
- **`ocr_events.segment_id`**：本地 OCR 事件是「畫面上出現過這段文字」的獨立紀錄，跟片段的關聯
  只是方便查詢；重新分析時 segments 會整批換掉但 OCR 事件不一定同步重跑，加外鍵反而會擋住合理的寫入。

## 5. FTS5 → PostgreSQL（全案唯一的技術風險）

### 5.1 目前依賴的是什麼

```
segments_fts (content, tokenize='trigram')   ← 專為中文選的：unicode61 無法比對中文子字串
  ├─ fts_bm25_search(terms)  → (segment_id, bm25 分數)，>= 3 字元的詞
  └─ fts_like_search(term)   → segment_id，< 3 字元的詞（trigram 查不到）
```

**關鍵發現**：`fusion.py` 的 RRF 只用 sparse 分數的**排序**（`sorted(sparse.items())` 後取 rank），
不用分數的絕對值。所以替代方案要保住的是**排名順序**，不是 bm25 數值。

但 IDF 加權不能丟。`sparse.py` 整套「短詞比例門檻」邏輯（`_SHORT_TERM_MAX_MATCH_RATIO = 0.2`）建立在
「長詞有真實 IDF 分數、短詞只有哨兵分數」的前提上——如果換成無 IDF 的純相似度排序，
「全壘打」（10 個片段命中）跟「畫面」（527 個片段命中）會被同等對待，排序會壞掉。

### 5.2 建議做法

**結構**：不建獨立的 FTS 表，改成在 `segments` 上加一個 generated column：

```sql
content TEXT GENERATED ALWAYS AS (
    COALESCE(transcript,'') || ' ' || COALESCE(visual_description,'') || ' ' || COALESCE(ocr_text,'')
) STORED
```
```sql
CREATE INDEX idx_segments_content_trgm ON segments USING gin (content gin_trgm_ops);
```

這一步是**淨簡化**：`content` 由資料庫自己維護，以下四段程式碼全部消失——

- `backfill_fts()`（補歷史資料）
- `prune_orphan_fts()`（清殘留列）
- `delete_for_video()` 裡同步刪 FTS 的那一段
- `insert_segment()` 裡手動組 content 再寫第二張表的那一段

順帶根除 `db/segments.py` 註解裡記載的那個真實 bug（實測 925/1795 = 52% 是殘留列，把真正命中的片段擠出候選集）。

**查詢**：`fts_bm25_search()` 改寫成一段 SQL，直接算 IDF × TF：

- 命中判斷：`content ILIKE '%' || term || '%'`（GIN trigram 索引可加速，>= 3 字元時）
- TF：`(length(content) - length(replace(content, term, ''))) / length(term)`
- IDF：`ln(總片段數 / 命中該詞的片段數)`
- 分數：`-SUM(idf * tf)`，加負號讓「越小越相關」的呼叫端語意不用改

`fts_like_search()` 幾乎照搬，`LIKE ?` → `ILIKE %s`。
< 3 字元的短詞用不到 trigram 索引會走 seq scan——931 筆，無感。

### 5.2.1 P0 spike 的實測結果（2026-08-27）

在真正動 P3 之前先在容器裡做了一次 spike（931 列中文假資料，形狀比照真實 segment 文字）：

- ✅ `content ILIKE '%全壘打%'` 對中文子字串比對**正確**——這是整個替代方案的地基，成立。
- ✅ `show_trgm('全壘打')` 產出 4 個 trigram（多位元組會先雜湊成 `0x...` 形式），中文確實進得了 trigram 索引。
- ⚠️ **意外發現**：`show_trgm('汽車')`（2 字元）產出 **3 個** trigram，不是 0 個——`pg_trgm` 會在詞前後補空白再切，
  所以 2 字元的詞在 PG 這邊**不是查不到**。

最後這點跟 SQLite 的行為有本質差異，必須寫下來避免之後誤改：

> SQLite FTS5 的 trigram tokenizer 對 < 3 字元的詞是**真的完全查不到**（產不出 token），`fts_like_search()`
> 這個 fallback 與 `sparse.py` 整套「短詞哨兵分數 ＋ 比例門檻」都是為了繞開這個限制而存在。
> PostgreSQL 這邊 `ILIKE '%汽車%'` **本來就找得到**，只是 2 字元的 pattern 用不到索引加速（要 3 個連續字元
> 才能從 pattern 抽出完整 trigram），走 seq scan 而已。

**因此的決定：P3 仍然保留 `fts_bm25_search()`／`fts_like_search()` 兩支函式與 `sparse.py` 的現有邏輯，
一行都不改。** 雖然技術上可以合併成單一支 ILIKE 查詢，但那會讓短詞從「哨兵分數」變成「真實 IDF 分數」，
是**搜尋排名的行為變更**——正好是 §11 明訂不做的事，也會讓 golden set 的差異無法歸因。

這個簡化留給遷移完成、指標確認沒退步之後，當成獨立的一次實驗來做（要重跑 golden set 驗證）。

### 5.3 驗收方式

專案已經有現成的量化工具：`scripts/run_golden_set_eval.py` + `docs/golden-set.csv`（18 題）。

1. **動工前**先在 SQLite 上跑一次，存成 baseline（結果自動寫進 `docs/eval-runs/<timestamp>.json`）。

## 8. pgvector 路線（未來，不在這次範圍）

動機 2 是「鋪路」，這裡把路寫下來，讓之後接手的人（或報告的「未來展望」）知道下一步長什麼樣。

**這次已經鋪好的**：pgvector extension 已安裝並啟用（P0-3），image 本身就帶著，不用再動環境。

**之後真的要換時的步驟**（獨立一個 branch 做）：

1. `segments` 加三個 `vector(1024)` 欄位（與現有 `BYTEA` 欄位並存，不是取代）。
2. 寫一支 backfill：讀 `BYTEA` → `decode_embedding()` → 寫 `vector` 欄位。兩份資料並存可逐一比對。
3. `dense.py` 的 `_score_video()` 從「全表讀進記憶體用 numpy 算 cosine」改成 SQL 的 `<=>` 運算子。
4. 加 HNSW 索引：`CREATE INDEX ON segments USING hnsw (transcript_embedding vector_cosine_ops)`。
5. 用同一份 golden set 驗證指標不退步，通過後才刪 `BYTEA` 欄位（依 CLAUDE.md，刪除前先問）。

**要誠實說的**：以目前 931 個 segments 的規模，這一步**不會讓搜尋變快**（numpy 全表算 cosine 只要毫秒級）。
它的價值是架構上的——資料量長到數萬片段時記憶體做法會撐不住。報告裡不要寫成效能優化。
