為什麼：db/ 已經是乾淨邊界，函式介面不用動。改 ORM 是另一個獨立專案（重寫 1348 行 ＋ 22 支測試），綁在一起會讓「搜尋結果變了」無法歸因。
D3Schema

FTS5 → pg_trgm ＋ 自算 IDF

GIN gin_trgm_ops 索引，分數在 SQL 內算 IDF × TF。

為什麼：PG 沒有 FTS5 對應物，而中文非用 trigram 不可。RRF 只吃排序不吃絕對值，但 IDF 不能丟。
D4範圍

pgvector 開 extension，欄位不換

embedding 維持 BYTEA 原樣搬。

為什麼：動機是「鋪路」不是「這次就上」。換 vector(1024) 要連帶改 analyzer.py／dense.py／embedding.py 的編解碼路徑，混在一起同樣會讓指標變動無法歸因。
D5範圍

時間欄位維持 TEXT

ISO-8601 字串，不改 timestamptz。

為什麼：6 個 dataclass 都宣告 created_at: str，且 ISO-8601 字串排序結果正確。改型別要動 dataclass ＋ API schema ＋ 前端格式化，收益只有「型別正確」。
D6策略

一次性切換，不做 dual-write

單機單人 app，可停機。

為什麼：雙寫的複雜度只有在「不能停機」時才值得付。回頭路是原封不動的 app.db 備份 ＋ git branch，30 秒。
D7策略

舊 app.db 保留不刪

複製到備份路徑，穩定跑一陣子後再問。

為什麼：CLAUDE.md 明訂刪檔一律先問；而且它同時是回滾用的安全網。

with conn 語意差異

sqlite3 只 commit 不 close，psycopg 是 commit 且 close。

對策：語意其實更正確（現況在漏連線）。已檢查過沒有程式碼在 with 區塊外用同一個 conn。
機率 低P5

測試改造工程量被低估

擔心 fixture 改動牽連一大片。

對策：已盤點——只有 6 處 fixture ＋ 2 支測試裡的直接 SQL，其餘 20 支完全不用動。
機率 低P4

id sequence 沒對齊

搬遷後保留原 id，但 identity sequence 還停在 1，下一筆 insert 撞主鍵。

對策：P4 明確列了 setval 步驟；驗證時插一筆再 rollback。
