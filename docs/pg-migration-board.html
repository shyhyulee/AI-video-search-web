核心結果：IDF 真的生效
  • 刻意設計的資料：全壘打 只命中 1 個片段（罕見）、畫面 命中全部 5 個（常見）
  • 實測分數：全壘打 −1.1458 vs 畫面 −0.0981——罕見詞好 11.7 倍
  • 這正是 sparse.py 的短詞比例門檻所依賴的鑑別力；IDF 沒保住的話這裡會是兩個相近數字，排序就壞了
  • OR 查詢中「同時命中兩個詞」的片段排第一，排序遞增（最相關在前），跟 SQLite bm25() 的介面契約一致
機械式改寫
  • ? → %s：videos 37、jobs 41、ocr_events 14、conversations 8、search_log 3
  • cursor.lastrowid → INSERT … RETURNING id（5 處）
  • MAX(COALESCE(…) != '') → bool_or(COALESCE(…) <> '')——PG 的比較結果是真布林，MAX(boolean) 會直接報錯
  • IN (?,?,?) 動態拼佔位符 → = ANY(%s) 直接吃 list
BM25 實作方式
  • PG 沒有等價內建函式（ts_rank 只吃 tsvector，對中文不能用），直接用 SQL 把公式寫出來
  • 參數對齊 SQLite FTS5 預設值：k1=1.2、b=0.75
  • 詞頻用「把該詞抽掉後少了幾個字元 ÷ 詞長」回推出現次數
  • 分數加負號，維持「越小越相關」的既有介面契約
兩個順手修掉的問題
  • 新增 _like_escape()：使用者查詢字串裡的 %／_ 現在會當普通字元比對。實測 fts_like_search("%") 回傳空 list 而不是全部片段
  • fts_like_search() 補 ORDER BY id：PG 的 LIMIT 沒有 ORDER BY 時回傳哪幾列不保證，而呼叫端要拿結果算比例門檻

已拍板的決定 2026-08-27 · 詳細理由見 docs/14 §3

D1環境

PostgreSQL 放 Docker

pgvector/pgvector:pg17，port 5433。Windows 端已裝的 PG17 保留不動。

為什麼：環境乾淨可重現，docker-compose.yml 進版控後整套環境是文件的一部分；直接用 pgvector 官方 image 等於鋪路零成本。
D2程式

psycopg3 ＋ 維持手寫 SQL

不引入 SQLAlchemy／Alembic。

為什麼：db/ 已經是乾淨邊界，函式介面不用動。改 ORM 是另一個獨立專案（重寫 1348 行 ＋ 22 支測試），綁在一起會讓「搜尋結果變了」無法歸因。
D3Schema

FTS5 → pg_trgm ＋ 自算 IDF

GIN gin_trgm_ops 索引，分數在 SQL 內算 IDF × TF。

為什麼：PG 沒有 FTS5 對應物，而中文非用 trigram 不可。RRF 只吃排序不吃絕對值，但 IDF 不能丟。
D4範圍

pgvector 開 extension，欄位不換

embedding 維持 BYTEA 原樣搬。

為什麼：動機是「鋪路」不是「這次就上」。換 vector(1024) 要連帶改 analyzer.py／dense.py／embedding.py 的編解碼路徑，混在一起同樣會讓指標變動無法歸因。
D5範圍

時間欄位維持 TEXT

ISO-8601 字串，不改 timestamptz。

為什麼：6 個 dataclass 都宣告 created_at: str，且 ISO-8601 字串排序結果正確。改型別要動 dataclass ＋ API schema ＋ 前端格式化，收益只有「型別正確」。
D6策略

一次性切換，不做 dual-write

單機單人 app，可停機。

為什麼：雙寫的複雜度只有在「不能停機」時才值得付。回頭路是原封不動的 app.db 備份 ＋ git branch，30 秒。
D7策略

舊 app.db 保留不刪

複製到備份路徑，穩定跑一陣子後再問。

為什麼：CLAUDE.md 明訂刪檔一律先問；而且它同時是回滾用的安全網。
