在本專案負責什麼

比較特別的是頁籤切換的方式。這個專案沒有用 <Routes>，而是自己寫了一層 keep-alive：每個造訪過的頁籤都留在 DOM 裡，只是非作用中的被隱藏起來。

這樣做的效果：切走再切回來時，該頁的 React state 原封不動——搜尋關鍵字與結果、展開中的卡片、進行中的分析 job、對話記錄都還在，捲動位置也還在。

在 render 中呼叫自己的 setState 看起來像 bug，其實是 React 官方認可的「render 期間調整 state」用法：有 includes 擋著不會無限迴圈，React 會直接重跑這個元件、不會多畫一幀，比放進 useEffect 少一次閃爍。

為什麼是這個做法

用 <Routes> 的話，切頁籤＝卸載舊頁、掛載新頁，所有 state 歸零。對這個應用來說代價太高：使用者在「片段搜尋」打完關鍵字、看了結果，切去「影片庫」確認一件事再切回來，結果全沒了要重搜一次（而且重搜要花錢）。keep-alive 是為了這個場景。

踩過的坑
display:none 會把捲動位置歸零

隱藏頁籤最直覺的寫法是 Tailwind 的 hidden（display:none），但那會讓元素失去 box，內部捲動容器的 scrollTop 被瀏覽器重設成 0，切回來會跳回最上面。改用 invisible（visibility:hidden）保留 box，捲動位置原封不動，而且同樣不會被鍵盤 focus 到、也不會被螢幕閱讀器讀到，不需要另外加 inert／aria-hidden。

背景頁籤的影片會繼續出聲

頁面留在 DOM 裡的副作用：切走之後 <video> 與 YouTube 內嵌播放器還在放。<video> 直接 .pause() 就好，但跨來源的 YouTube iframe 沒有 DOM API 可以控制，只能用 IFrame Player API 的 postMessage 指令，而且 embed 網址要帶 enablejsapi=1（見 components/YoutubeResultCard.tsx）。

為什麼 workers=1（這條很重要）

單一 worker process 是刻意的簡化，而且有三個地方依賴它。改成多 worker，這三處會安靜地壞掉：

要水平擴展就得把這三處重新設計（分散式鎖、共用快取）。目前的規模不需要，所以把約束寫進 api/main.py 的模組 docstring，讓下一個人看得到。

L2-05 Job Manager 自製 services/job_manager.py
一句話定位

把「背景執行緒 ＋ queue 進度事件」接上資料庫的一層薄膠水，讓工作狀態能跨 HTTP request 查詢，並保證同時只有一支影片在分析。

在本專案負責什麼

這是五層裡唯一自己寫的「技術」，252 行，沒有引入任何工作佇列套件（Celery／RQ／Dramatiq）。它做四件事：

  • 序列化分析工作——同時只有一個 analysis job 在 running
  • 把進度落地——原本會被 Tk widget 讀走的 queue 事件，改成寫進 jobs 表
  • 重試——失敗的工作可以重新 submit（建新列，舊列留作歷史）
  • 啟動時清理殭屍工作——上次 process 被砍掉、卡在 running 的全部標記失敗

設計上的重點：不改動 analyzer.py／downloader.py 任何一行既有的 threading／併發邏輯。那些程式碼原本是 Tkinter 版就有的，Web 版只是換了一個讀 queue 的人。

關鍵實作：序列化 dispatcher

鎖只保護「檢查＋標記」這一步，避免多個呼叫端同時通過檢查；真正啟動工作在鎖外面。

為什麼不用 threading.Semaphore(1)

效果等價，但 Semaphore 只知道「有沒有空位」，不知道下一個該跑哪個 job。這裡需要「空出來時，挑最舊的一筆 queued 分析工作」，所以用旗標＋DB 查詢實作。

關鍵實作：pump thread

每個工作配一條 pump thread，把 analyzer 送出的事件搬進 jobs 表：

執行緒有取名字（job-pump-analysis-{id}，job_manager.py:120），traceback 與 py-spy 看得出這條在做什麼，測試也能等它收尾。

踩過的坑
釋放 slot 一定要放在 finally

pump 迴圈裡每一次資料庫寫入都可能失敗。只要這條 pump 沒走到釋放那一步，_analysis_running 就永遠是 True，之後所有分析都卡在 queued，而且沒有任何錯誤訊息——畫面上只會看到工作排隊排到天荒地老。analyzer 那邊保證一定會送出終端事件，finally 是第二道防線。

狀態變更必須排在所有驗證之後

submit_analysis(reanalysis=True) 會把影片切到「重新分析」狀態。這一步一定要排在三個驗證通過之後：先改狀態再驗證的話，任何一個驗證失敗都會留下一支狀態已被改掉、卻沒有任何工作在跑的影片，畫面上永遠停在「等待重新分析」。

刻意不做的事

沒有 Cancel。 pipeline 沒有 checkpoint、也沒有取消 token，要做「真取消」得把訊號貫穿進每一個 phase 函式。與其做一個按了會停在不確定狀態的假取消，不如不做——這也是 jobs 表的狀態只有 queued／running／completed／failed 四種、沒有 cancelled／retrying 的原因。

下載工作不序列化。 下載不呼叫 OpenAI、不消耗 BUDGET_USD，序列化沒有意義，收到請求就立即開始（job_manager.py:175-193）。

merge 先、split 後的順序有意義：如果 split 先做，merge 可能把切好的片段黏回去、又超過長度上限；merge 先做、split 當最後一道保險，才能確保最終長度上限。

為什麼是兩個 detector 聯集

ContentDetector 單獨使用會漏掉漸進式轉場（溶接／crossfade）。實測用《The 100 Most Beautiful Faces of 2019》前 3 分鐘比對，它把 45.88~180.01 秒整整 134 秒判成單一場景，但那段裡其實有至少 5 個不同人物條目（用溶接轉場）。加上 AdaptiveDetector 取聯集（任一個判定切就切）能正確抓出中間漏掉的切點，而且實測耗時幾乎沒差——decode 才是瓶頸，不是 detector 運算量。

也評估過 ThresholdDetector（偵測淡入淡出黑幕）：同一支影片實測除了抓到片頭真的從黑幕淡入的切點，也在完全靜止的片頭卡誤切出一個假場景，false positive 風險偏高，不採用。

原始場景長度落差極大——實測同一支影片有 0.10 秒到 129.76 秒都有。目標帶調過三次：

關鍵是那條「2× 下限」限制：只有當 SPLIT_ABOVE_SEC >= 2 × MERGE_BELOW_SEC 時，把超長場景切 2 段才保證兩段都不低於下限。目標帶越窄，落在「切了會低於下限、不切又超過上限」這個死區的場景就越多，會保留成超長片段。

取捨方向也是明確的：寧可片段偶爾超過上限，也不要低於下限——下限存在的目的是避免 VLM／OCR 只看到一小段畫面，這比切出來的片段稍微超長更傷。

踩過的坑
AV1 影片會被判成「整支只有一個場景」

scenedetect 預設的 opencv backend 在這台機器上無法解碼 AV1：沒有硬體加速，軟體解碼路徑直接讀不到任何畫面（回傳 0 frame）。可怕的是它不會報錯，會被誤判成「整支影片只有一個場景」，而不是「偵測不到切換」。YouTube 常見的 720p 串流時常是 AV1，所以踩到的機率不低。

解法是先用 ffprobe 確認編碼，AV1 才切換成 pyav backend（用 ffmpeg 自己的解碼器，能正確處理但明顯較慢——實測 602 秒影片，pyav 約 85 秒 vs opencv 約 19 秒）。

進度條是估的，不是真的

PySceneDetect 不提供逐步進度——SceneManager 的 callback 只在偵測到場景切換時觸發，分佈不均勻，不適合做平滑百分比。所以改用背景執行緒等待期間依經驗校準的預估時間回報百分比（progress_estimation.py），兩個 ratio 常數就是那組校準值，各留了安全邊際。顯示上限 95%（MAX_DISPLAY_PERCENT），避免估到 100% 但實際還沒跑完。

模式 A 的門檻怎麼來的：真實對白影片的 no_speech_prob 最高值只有 0.264~0.487，幻覺片段（例如背景音樂被誤判成「ក្រាមំ ក្រាមំ」）集中在 0.7~0.985。中間有明顯空隙，所以 0.7 不會誤殺。

模式 B 為什麼需要兩個條件同時成立：真實內容最長連續符合「主導詞佔比 ≥ 0.5 且跟前一場景主導詞相同」只到 2，幻覺案例最低是 4，門檻定 3 留緩衝。單獨用任一條件都會誤殺——只看「主導詞佔比」會誤殺短促的動物教學內容，只看「連續同一主導詞」會誤殺英文長句裡 the 這種高頻虛詞造成的巧合。

判定為幻覺之後做什麼

不建立字幕 embedding（讓它搜不到），但 segments.transcript 仍然照實際 Whisper 輸出寫入。不隱藏原始內容，只是不讓它污染搜尋索引（analyzer.py:562-563）。

踩過的坑
約 52 分鐘以上的影片會先卡在 ASR，而不是預算

MAX_DURATION_SEC 放寬到 60 分鐘後，真正的瓶頸不是錢。_extract_audio() 固定輸出 64kbps 單聲道 mp3（實測 7,998 bytes/s），Whisper 的 25MB 上傳上限換算後約 52~55 分鐘。而且 ASR 例外會讓整支分析失敗（不是像 VLM 那樣略過該場景），所以超過約 52 分鐘的影片會先在這裡爆掉，走不到預算判斷。

分數彙總的方式不對稱

scores_for_range() 把重疊片段的 no_speech_prob／avg_logprob 取平均，compression_ratio 取最大值——範圍內只要有一段重複就該被看見，取平均會被較長的正常內容稀釋掉（asr.py:103-115）。

L4-04 pg_trgm ＋ GIN 索引 extension db/segments.py
一句話定位

把字串拆成三字元片段（trigram）來加速子字串比對的 PostgreSQL extension；GIN 是它用的倒排索引型別。

在本專案負責什麼

撐起關鍵字檢索（sparse channel）。比對來源是一個 generated column——三個模態的文字自動串起來，由資料庫自己維護：

為什麼是 trigram 而不是內建全文檢索

PostgreSQL 內建的 to_tsvector 全文檢索對中文不能用：中文沒有空白斷詞，'simple' parser 會把整句當成一個 token，子字串完全比對不到。要正確斷中文詞得裝 zhparser／pgroonga 這類額外 extension。

trigram 不需要斷詞就能比對中文子字串——跟 SQLite 時期選 tokenize='trigram' 是同一個理由，遷移前後的檢索語意因此保持一致。

3 字元的門檻：SQLite 是硬限制，PostgreSQL 只是效能差異

GIN 索引只在 pattern 有 3 個以上連續字元時才吃得到（要抽得出完整 trigram）。2 字元的詞在 PostgreSQL 仍然查得到，只是走 seq scan——這跟 SQLite FTS5「<3 字元完全查不到」不同。這個差異刻意沒有拿來改搜尋行為：sparse.py 仍然只送 ≥3 字元的詞進 BM25，短詞走 LIKE fallback，維持遷移前的排序語意。

踩過的坑（這是整個專案最值得讀的一個 bug）
FTS 殘留列吃掉 52% 的候選名額

SQLite 時期 segments_fts 是獨立的 FTS5 虛擬表，rowid 靠呼叫端自己跟 segments.id 同步。刪片段時只 DELETE FROM segments、忘了刪 FTS 對應列，就會留下一堆對不到片段的殘留列。

為什麼致命：fts_bm25_search() 是「先取 BM25 前 200 名、再由 sparse.py 過濾掉不存在的 id」。殘留列會佔掉那 200 個名額，把真正命中的片段擠出候選集——搜尋結果會安靜地變差，沒有任何錯誤訊息。實測一支用了一陣子的 app.db：925/1795、52% 是殘留列。

改成 generated column 之後，content 隨著 DELETE FROM segments 一起消失，這整類問題在結構上不存在了。這是「把約束交給資料庫」勝過「靠呼叫端自律」的教科書案例。

為什麼三個模態分開 embed，不混成一條向量

這是這一層最重要的設計決定。如果把字幕＋畫面描述＋OCR 串成一段文字再 embed 成單一向量：

  • 長的模態會稀釋短的——一段話很多的字幕會蓋掉「畫面上出現三個字」的 OCR 訊號。
  • 失去可解釋性——沒辦法告訴使用者「這個片段是靠字幕命中還是靠畫面命中」。搜尋結果的 hit_source（字幕／畫面／OCR／綜合）就是靠分開的分數算出來的。
  • 沒有內容的模態會變成雜訊——純畫面無字幕的片段，串接後會多出一段空白。

分開之後，每個模態各自比對、取最高分當作這個片段的 similarity（service.py:70）。三個分數也一起回傳給前端，就是證據面板上那三條。

踩過的坑
不同模型的向量空間不可混用

模組 docstring 開頭就寫了這句話。換 embedding 模型等於全部片段的向量作廢，必須重新分析全部影片——沒有漸進遷移路徑。segments.embedding_model 欄位記著當初是用哪個模型產生的，就是為了讓這種不一致查得出來。

一句話定位

資訊檢索的標準關鍵字排序函式：詞頻越高越相關、但會飽和；詞越罕見（IDF 越高）越有價值；文件越長越要打折。

sparse channel 的評分。特別的是——PostgreSQL 沒有內建 BM25，這裡是直接用 SQL 把公式寫出來的。SQLite 時期用的是 FTS5 內建的 bm25()，遷移後沒有等價函式（ts_rank 只做 tsvector，對中文不能用），所以自己算。

關鍵實作：公式怎麼寫成 SQL

兩個值得注意的技巧：

  • 詞頻的算法：中文沒有空白斷詞，不能用「切成詞再數」。這裡用「把該詞全部抽掉之後 content 少了幾個字元，除以詞長」回推出現次數。
  • 分數加負號：呼叫端（sparse.py／fusion.py）沿用 SQLite bm25() 的慣例——數字越小（越負）代表越相關。這個介面契約在遷移中刻意不變。

930 個片段的規模下這個查詢是毫秒級。

為什麼一定要保住 IDF

這不是理論潔癖，是有實測後果的。sparse.py 整套短詞比例門檻邏輯建立在「長詞有真實 IDF 加權」的前提上——實測「全壘打」只命中 10 個片段、「畫面」命中 527 個。沒有 IDF 的話兩者會被同等對待，排序整個跑掉。

短詞的三層防護

<3 字元的詞走 LIKE fallback，但直接把它們當成命中會製造災難。所以有三層設計：

機制值擋什麼
_SHORT_TERM_SPARSE_SCORE-1e6讓短詞精確命中排在所有真實 BM25 分數（-2~-10）前面
setdefault（不覆寫）sparse.py:61只補「完全沒被長詞 BM25 找到」的片段
_SHORT_TERM_MAX_MATCH_RATIO0.2比對到 >20% 候選的短詞整個跳過

第二層的必要性：實測「找出全壘打的畫面」會同時拆出一個罕見長詞（「全壘打」，10 個片段命中）跟一個常見短詞（「畫面」，527 個片段命中）。如果短詞哨兵分數無條件覆寫，527 個只是剛好提到「畫面」的片段會並列蓋過真正命中「全壘打」的片段。

第三層的校準：用同一支 app.db 的幾個詞驗證方向——汽車 11.6%／工廠 14.4%（有鑑別力，該保留）vs 畫面 77.4%（沒有鑑別力，該跳過）。0.2 剛好能把兩種情況分開。用比例而非絕對筆數，這樣全域搜尋與限定單一影片搜尋都適用。

順帶做的事：否定句排除

「不要出現機器人」這種查詢，會用同一套取詞規則對否定範圍的文字跑一次比對，命中的片段直接從候選集拿掉（sparse.negated_segment_ids()、service.py:48-53）。重用 sparse_scores() 的好處是連 _SHORT_TERM_MAX_MATCH_RATIO 防呆一起繼承——避免否定詞剛好是「畫面」這種泛用詞時誤刪掉大部分候選。

已知限制

否定只在關鍵字比對層有效。「不要出現機器人」能排除字面命中「機器人」的片段，但語意向量看不懂否定，用「機械手臂」描述的畫面仍會被撈進來。見 docs/05。

L5-04 RRF（Reciprocal Rank Fusion） k=5 search/fusion.py
一句話定位

融合多個排序清單的方法：score = Σ 1/(k + rank)。只看名次不看原始分數，所以不需要把不同尺度的分數正規化。

在本專案負責什麼

把 dense 排名與 sparse 排名合成最終排序依據。這正是 RRF 適合這裡的原因——dense 分數是 0~1 的 cosine、sparse 分數是 -2~-10 的 BM25，兩者沒有共同尺度，硬要加權相加就得先想辦法正規化，而正規化本身又是一組要調的參數。

沒被某個 channel 找到的片段，該 channel 對它的貢獻是 0，不是懲罰分數。 dense 排名涵蓋全部候選片段（不是只有 top_k）。

關鍵參數與實際值
參數值位置

k=5 而不是業界常見的 60：k 越大，前後名次的分數差距越小（越「平等」）。實測候選片段數多（一兩百個）時，k=60 會讓「兩個 channel 都中等」贏過「單一 channel 命中得很準」。調小讓 top rank 的優勢更明顯。

註解與程式碼有一處不一致

fusion.py:9 的註解寫「k=60 是業界常見的保守慣例值」，緊接著第 13 行是 RRF_K = 5。註解是在說明調參的起點與理由，不是說現值是 60——但單看那一行很容易誤讀。實際生效的是 5，投影片寫的也是 5。

兩個門檻，兩件不同的事

排序完之後還有兩個判斷，很容易搞混：

similarity 與 fusion_score 是分開的兩件事

similarity 保留的是「這個片段最強模態的原始 cosine」，RRF 只決定排列順序、不覆寫這個欄位。所以列表可能出現 similarity 較低的片段排在前面——那代表它被兩個通道都找到了。SearchResult.fusion_score 額外把 RRF 分數本身帶出來，讓呼叫端能解釋排序依據（search/results.py:3-7）。

踩過的坑

這兩個值是使用者直接指定的門檻，不是實測校準的結果（fusion.py:19 明講了）。調它們會直接改變「找不到結果」的頻率，動之前先跑一次 Golden Set 評測（scripts/run_golden_set_eval.py）。

  • max_workers=1 也是平行的——轉錄丟進 pool、場景切分留在主執行緒，兩者同時跑，只是不需要第二個 worker。
  • future.result() 不能放進 finally：場景切分失敗時例外會在上一行就往外拋，往外傳的一定是場景切分自己的例外。放進 finally 的話，轉錄如果也失敗就會反過來蓋掉它，使用者看到的失敗原因會是錯的。有測試鎖住這個情況。
進度回報

兩者都用預估進度而非真實進度（PySceneDetect 的 callback 分佈不均、Whisper API 不回報進度）。顯示上限 95%（progress_estimation.MAX_DISPLAY_PERCENT），輪詢間隔 0.4 秒。使用者看到的是「場景切分中 62%（預估）」——括號裡的字是刻意的誠實標示。

失敗會怎樣

兩者都會讓整支分析失敗。 這跟後面的 VLM／OCR／摘要不同——那三個是「失敗只跳過自己」，這兩個是必要輸入，沒有就沒得做。例外往上冒到 _run_analysis() 的 except，寫 STATUS_FAILED 並送出 AnalysisError。

失敗訊息會標出是哪個階段

B §7 橫切：預算護欄與成本記帳 BUDGET_USD = 0.80
機制

整條 pipeline 共用一個 _AnalysisContext，它同時負責進度回報與累計花費／預算判斷。抽出這個物件的理由很實際——這兩件事原本靠參數手工穿過每個 phase 函式，新增或調整一個 phase 就要同時記得三件事（更新 pipeline_stage、送出 AnalysisProgress、累加並回傳花費），漏掉任何一件都不會報錯，只會安靜地少一個進度或少算一筆錢。

有鎖，因為好幾個 phase 是在背景執行緒裡累加花費（音訊轉錄、本地 OCR）。呼叫端不用各自想同步問題。

$0.80 是怎麼算出來的

成本模型：

60 分鐘影片：實測密度下平均約 $0.55、最壞觀測費率約 $0.70。

關鍵在於片段密度不會失控——場景正規化保證每段至少 8 秒（L3-02），所以密度的結構上限是 60/8 = 7.5 個/分，快剪內容也一樣。用「結構上限密度 × 最高觀測每片段費率」算出的最壞情況是 $0.765，仍在 $0.80 內（餘裕僅 4.6%）。
