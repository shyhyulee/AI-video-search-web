過程記錄 做錯、走錯、以及沒做乾淨的地方

P1我的 bugB1

突變測試還原時，把未提交的程式碼一起刪掉

用 git checkout -- 還原臨時改壞的檔案，但那個檔案的 B1 新程式碼還沒 commit， 於是連同一起被還原掉。重新補回後才發現。

之後的做法：突變測試一律先 cp 備份，還原時用備份覆蓋， 並且用 diff -q 確認還原後的內容真的是改好的版本。
P2寫錯註解B3

註解宣稱了一個不存在的因果

我寫「result() 放在 with 之外是為了不讓轉錄的例外蓋掉場景切分的例外」—— 突變測試證明放進 with 內外沒有任何差別，因為場景切分的例外在前一行就往外拋了。

修正：真正會破壞語意的是把它放進 finally。註解已改成講這件事， 並補上一支會因此轉紅的測試。
P3我的 bugC0

測試用 monkeypatch.undo()，連 fixture 的 patch 一起撤掉

兩支測試在中途呼叫 undo() 想還原假的 db 函式，但它會撤銷該測試的全部 monkeypatch，包含 fixture 設的 db.DB_PATH——後半段其實在讀真正的 app.db。

為什麼一直沒發現：主目錄剛好有 app.db，所以一路綠燈。 是把每個 commit 匯出成獨立副本驗證時才炸出 no such table: jobs。已改用旗標控制假實作。
P4走錯方向C0

為了修測試洩漏，讓全套測試從 6 秒變成 104 秒

我在 fixture 收尾等「所有 pump thread 結束」，但很多測試刻意讓 pump 停在 queue.get() 不送終端事件——等它們只是純粹等到逾時，每支 3 秒。

修正：改回有界等待。保留了 pump thread 命名這個副產物， 它對 production 追問題（traceback／py-spy）有實際價值。
P5沒做乾淨切 commit

三個 commit 的切分不是 100% 乾淨

_start_analysis_job 的 assert → raise 原本規劃在第二個 commit， 但它就在 thread 命名的上方兩行，被第一個 commit 的 hunk 吸收了。

沒有硬拆：位置本來就合理（同一個函式），而且三個 commit 都各自 獨立驗證過是綠的。為了帳面整齊去拆會增加風險而不是降低。
