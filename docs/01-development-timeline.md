## 2026-08-18：UI 重寫與 Pipeline V0

### 全域 UI 骨架

- 建立集中管理的 Theme（顏色、8px 間距系統、字型、`ttk.Style`）、共用小型元件（`StatCard`／`EmptyState`／`Badge`／`SimilarityBar`／可捲動 Treeview）、全域 Header（四張統計卡）、主視窗與四頁籤 Navigation。
- 開發環境問題：`uv` 自動下載的 standalone Python 在 WSL2+WSLg 上 `tkinter` 找不到 CJK 字型，中文全部顯示空白。修法：強制 `uv` 使用系統 Python（`pyproject.toml` 的 `python-preference = "only-system"`）。

### YouTube 下載＋待分析清單（真實功能）

- `downloader.py` 包 `yt-dlp`，固定 720p，背景執行緒下載＋Queue 回報進度。
- **修正下載 403 Forbidden**：YouTube 對多數 player client 要求 PO Token 才能取得影片本體，改用不需要 PO Token 的 `web_embedded` client，並加上 `js_runtimes: {"node": {}}` 解簽章挑戰（新增系統依賴 `node`，已用 v22.22.1 驗證）。

### 「開始分析」核心 Pipeline V0（真實功能）

打通「下載 → 分析 → 寫入索引 → 能被找到」的最短路徑：`scene_detect.py`（PySceneDetect）、`asr.py`（Whisper）、`vlm.py`（GPT-4o-mini 畫面描述）、`embedding.py`（`text-embedding-3-small`，字幕與畫面**分開** embed）、`analyzer.py`（background thread orchestrator，Queue 回報進度，超過 US$0.20 立刻停止並標記部分完成）、`search.py`（brute-force cosine，取較高分排序）。

驗證：真實 YouTube 影片（19 秒 "Me at the zoo"）跑通全流程，`segments` 正確寫入，花費 US$0.0025，搜尋語意排序正確（「大象」相似度 0.51 vs「棒球比賽」相似度 0.15）。

### 修正 AV1 場景切分失效

`web_embedded` client 抓到的 720p 影片常是 AV1 編碼，PySceneDetect 預設的 `opencv` backend 沒有硬體加速時對 AV1 完全讀不到畫面，誤判成「整支影片只有一個場景」。改用 `ffprobe` 先偵測編碼，AV1 才切換 `pyav` backend（新增依賴 `av`，較慢，602 秒影片需 79～85 秒）。602 秒影片原本誤判成 1 個場景，修正後正確找到 19 個。

### 進度百分比（音訊轉錄＋場景切分）

Whisper API／PySceneDetect 都不提供伺服器端進度，改用背景執行緒等待期間依經驗校準的預估時間定期回報百分比（上限顯示 95%，避免顯示到 100% 但還沒真的完成）。

### 影片庫頁籤（真實功能）

`pipeline/summary.py`（GPT-4o-mini 產生 3～5 行摘要）、`list_library_videos()`（`analyzed`＋`failed` 都顯示）、影片庫列表（排序／篩選／縮圖／詳細面板／「重新產生摘要」／「在此影片內搜尋」）。過程中修掉兩個真實 bug：

1. **Tk `<<TreeviewSelect>>` 事件是非同步派發的**：`refresh()` 為保留選取重新 `selection_set()` 同一列，會觸發延遲的 select 事件，把剛顯示的「✓ 摘要已更新」訊息洗掉。修法：只有「使用者真的選了不同影片」才清暫時性訊息。
2. **影片庫沒有即時顯示新分析完的影片**：自動刷新原本只綁在切換分頁那一刻，如果分析完成當下使用者剛好停在影片庫分頁就不會更新。修法：`_on_stats_changed()` 統一觸發 `library_tab.refresh()`。

### Whisper 信心分數欄位（只做擷取，未做過濾）

發現背景音樂被 Whisper 轉錄成大量重複歌詞，污染字幕 embedding。這次先把 Whisper API 本來就有回傳、但先前沒儲存的 `no_speech_prob`／`avg_logprob`／`compression_ratio` 存進 `segments` 表，過濾邏輯留到 08-20 才做（見下方「Whisper 幻覺字幕過濾」）。

### OCR（畫面文字）支援

用 OpenAI structured output 讓 GPT-4o-mini **在同一次 VLM 呼叫**裡同時回傳畫面描述與畫面文字，不需要傳統 OCR 引擎、成本幾乎不變。所有 embedding 向量統一設定成 **1024 維**（`text-embedding-3-small` 原生 1536 維，用 API 的 `dimensions` 參數截短）。

## 2026-08-19：本地 OCR 與搜尋強化

### 本地 OCR 雙引擎 Phase 1（EasyOCR MVP）

補上 VLM-OCR 只在場景中點抽一張畫面、可能漏掉其他時間點文字的缺口。新增 `pipeline/frames.py`（共用抽幀）、`pipeline/ocr_adapters.py`（`OcrEngine` Protocol＋`EasyOcrEngine`，`lru_cache` 單例）、`pipeline/ocr_service.py`（場景內固定間隔取樣＋正規化＋去重合併）、`ocr_events` 表。**這是專案第一次有自動化測試**（`pytest` 加入 dev dependency，15 個 unit test）。

端到端驗證：自製測試影片（文字只在 1～3 秒可見，VLM 中點在 6 秒抓不到），本地 OCR 在 2 秒取樣點正確抓到文字（confidence 0.996），搜尋正確以 `hit_source='OCR'` 命中，沒有污染其他模態分數。花費 US$0.00168。

### 場景切分改用多 Detector 聯集

`ContentDetector` 單獨會漏掉漸進式轉場（溶接／crossfade）。改用 `ContentDetector`＋`AdaptiveDetector`（PySceneDetect 的多 detector 是聯集關係：任一個判定切就切）能正確抓出中間漏掉的切點。曾評估加 `ThresholdDetector`，因誤切率偏高而不採用（見 [`03-excluded-approaches.md`](03-excluded-approaches.md)）。602 秒測試影片場景數從 19 增加到 33，耗時幾乎沒差（88.5s vs 校準值約 85s）。

### 場景長度正規化（merge/split）

原始場景長度落差極大（0.1～129.76 秒都有）。新增兩個 pass：合併太短場景、切開太長場景，收斂到約 6～12 秒。33 個原始場景 → merge 後 21 個 → split 後 69 個，96%（66/69）落在 6～12 秒範圍內。

### 搜尋支援中英文雙語查詢

查詢先翻譯成中英文兩個版本各自 embed，每個模態取兩者較高分。實測跨語言比對（英文畫面描述 vs 中文查詢「警告標誌」）分數從 0.5624（不翻譯）提升到 0.6704（翻譯後）。

### 自動摘要（Phase F）＋搜尋依摘要篩選影片＋搜尋成本追蹤

三件相關的事一起做：`analyzer.py` 新增 Phase F 自動產生摘要；`search()` 新增 `_relevant_video_ids()`，全域搜尋先依影片摘要（無摘要退回標題）篩選相關影片；新增 `search_log` 表追蹤每次搜尋花費。**實測抓到真的門檻校準問題**：短標題估出的 `MIN_RELEVANCE=0.25` 對長摘要文字太嚴格（明確相關查詢的最高分只有 0.22），改成以相對差距 `RELEVANCE_MARGIN=0.15` 為主要判斷依據，詳見 [`02-technical-decisions.md`](02-technical-decisions.md#影片層級篩選)。

## 2026-08-20：搜尋準確率 Phase 1、平行化、重構

> 這天的工作原本散落在各規劃文件自己的「狀態」列，此節統一補上。（當時的 `development-log.md` 索引只更新到 08-19，該檔案與 `changelog/` 現已不存在，本文件是唯一的開發歷程記錄。）

### Golden Set 定案與 Evaluator

修正 CSV 編碼，刪除有資料矛盾的 `gs-009`，定案為 17 題（13 題 answerable、4 題 no-answer）。新增 `pipeline/evaluation.py`：Recall@K、MRR、nDCG@K、Timestamp IoU、No-answer F1，純邏輯評分函式與需要真實 API 的整合函式分離。詳見 [`04-testing-and-evaluation.md`](04-testing-and-evaluation.md)。

### Hybrid 檢索（Dense + BM25 FTS5 trigram）+ RRF 融合

`search.py` 排序從純 dense cosine 改成 RRF（Reciprocal Rank Fusion）融合 dense 排名與 BM25/LIKE 關鍵字排名。掃過 `RRF_K` = 60/20/10/5 四個值，隨 k 變小持續單調變好，定案 **`RRF_K=5`**。對照 baseline：Recall@1 0.538→0.615、Recall@5 0.692→0.846、MRR 0.628→0.722、nDCG@5 0.636→0.746、Mean IoU 0.725→0.773，全部超過純 dense baseline。詳見 [`02-technical-decisions.md`](02-technical-decisions.md#hybrid-檢索與-rrf-融合)。

### 無答案信心判斷

`no_answer_f1` 原本用借來的 `MIN_RELEVANCE` 門檻恆為 0。探索四種訊號後，只有「top1 是否同時被 sparse channel 印證」這個布林訊號能把 answerable／no_answer 兩組分開。新增 `SearchResponse.is_confident`，`no_answer_f1` 從 0.000 提升到 **0.667**，Recall@5／Mean IoU 完全不受影響。已知限制：無法處理否定句。

### 場景長度目標帶收窄：6～12 → 9～12 → 8～12 秒

使用者希望片段更完整，先試 9～12 秒，發現命中率不升反降（67.7%～91.1%），根因是數學上的「死區」（`SPLIT_ABOVE_SEC` 不再等於 `2×MERGE_BELOW_SEC`）放大了既有邊界情況，順便修掉這個被放大的 bug。改成 8～12 秒後命中率回升到 78.8%～91.4%，下限保證兩支測試影片都是 100% 沒違反。**這個常數變更讓 golden-set.csv 既有的時間戳基準需要重新產生**，詳見 [`04-testing-and-evaluation.md`](04-testing-and-evaluation.md#5-評測-baseline-的時效性警示)。

### 影片下載平行化實驗（aria2c）—已放棄

嘗試用 aria2c 多連線加速下載，實測反而比原生單連線下載器慢 4～7 倍（15.8s vs 65.6s/109.1s）。已回滾，詳見 [`03-excluded-approaches.md`](03-excluded-approaches.md)。

### 分析流程平行化（Tier 1 + Tier 2）

在不改變任何判斷結果的前提下縮短分析耗時：Tier 1（零風險）— 場景切分＋音訊轉錄同時起跑、片段內三個 embedding 平行送出、本地 OCR＋產生摘要同時起跑。Tier 2 — VLM 逐場景畫面分析改成批次平行（`VLM_BATCH_SIZE=5`，依真實撞過的 TPM 上限回推）＋新增 rate limit 重試機制。真實效能驗證：20 個真實場景，批次平行 13.2 秒 vs 循序估算 57.3 秒，**加速 4.35 倍**，0 次撞 rate limit。詳見 [`02-technical-decisions.md`](02-technical-decisions.md#分析流程平行化)。

### UI：新增「融合分數」欄位

使用者發現搜尋結果排名沒有依照畫面上「相似度」欄位由高到低排序，追查後確認是刻意設計（排序依 RRF 融合分數，相似度只顯示 dense cosine 分數，兩者本來就是分開的數字）。`SearchResult` 新增 `fusion_score` 欄位，UI 結果列表／詳細面板／CSV 匯出都新增「融合分數」對照顯示，避免使用者誤讀。

### 重構（第一輪＋第二輪）

依 `.claude/skills/refactor/SKILL.md` 進行兩輪不改變外部行為的重構：

- **第一輪（Step 1～9）**：刪除死碼（`mock_data.py`、未使用函式）、抽出共用的 `pipeline/progress_estimation.py`（場景切分與音訊轉錄的背景執行緒＋預估進度邏輯，原本逐字重複）、`db.py` 拆成 `db/` 套件（`connection`／`videos`／`segments`／`ocr_events`／`search_log`，對外 API 不變）、`analyzer.py` 的 `_analyze_worker()` 拆成具名 phase 函式、新增特徵測試（`test_db.py`／`test_analyzer_integration.py`）、`development-log.md`（原 35KB 單檔）依日期拆成 `changelog/`。UI 輪詢骨架抽取（原規劃的 Step 10）評估後判斷效益低於風險，**明確決定不做**。
- **第二輪**：修正 3 處指向已搬移文件的殘留註解引用；補上 `search._hit_source()` 的測試；抽出 `openai_client.chat_completion_cost()` 共用 helper，取代 `vlm.py`／`summary.py`／`translation.py` 三處逐字重複的成本計算公式；`analyzer.py` 的 `segment_rows` 從無型別 9-tuple 改成具名 `_SegmentRow` dataclass。兩輪重構全程遵守「先分析、確認後才動手、一次只做一步、每步都跑測試驗證」的流程；第二輪結束時全專案 150 個測試（不含需要真實 API 的 `integration` 測試）全數通過。

### 重構（第三輪）

依 `.claude/skills/refactor/SKILL.md` 進行第三輪不改變外部行為的重構。這一輪的範圍是**Web 化之後長出來的東西**：新增的 services／schemas／api 三層，以及在遷移期間成長到 697 行的 `analyzer.py`。分三波共 8 個 commit，測試從 266 增加到 **326**：

- **波 A（安全網，先補測試不動正式碼）**：`job_manager` 是全專案唯一有 process 級共享狀態（分析 slot 旗標＋鎖）與 pump thread 的模組，卻只有 HTTP 層的間接測試；`search()` 的 helper 全都有測試，但「串起來之後」的行為沒有。補上 `test_job_manager.py`（27 支）與 `test_search_pipeline.py`（17 支），後者用真實臨時 SQLite（含 FTS5 bm25），只把兩個 OpenAI 呼叫換掉，向量刻意用 4 維讓 cosine 值可人工推算。兩支都做過突變測試確認不是空轉。
- **波 B（結構）**：① `GET /api/v1/videos` 為了算三個布林旗標而載入每支影片的全部 segment（含 embedding BLOB），改成一句聚合查詢，實測 **47.5ms → 0.7ms**、省下每次請求約 4.5MB 的 BLOB 讀取；② `analyzer.py` 的進度回報、成本累加與預算判斷三個橫切關注點原本靠參數手工穿線（`total_cost` 出現 43 次、進度雙寫 23 處），收進 `_AnalysisContext`（**43 → 7**，`_run_vlm_phase` 參數 7 → 3）；③ 兩處手工「Thread ＋ holder dict ＋ 手動重拋」改用 `ThreadPoolExecutor`，全檔只剩一種併發寫法；④ `search.py`（522 行單檔、`search()` 一個函式做六件事）拆成 `pipeline/search/` 七個模組，依賴單向無環，對外 import 路徑完全不變。
- **波 C（一致性）**：例外型別從 `job_manager` 搬到 `services/errors.py`（API 原本有 5 處拿 `job_manager.VideoNotFoundError` 表達「影片找不到」）；API 層 6 處繞過 service 直呼 `db` **收斂為 0**，順帶消掉 4 個 `assert`（`python -O` 下會整個消失）；補上全專案第一份 logging 設定（在這之前所有訊息只能靠 lastResort handler 印出，INFO 完全看不到），5 處 eager f-string 改 lazy `%`、3 處沒有 consumer 的 `extra={…}` 移除；20 處引用早已移除的 Tkinter UI 的註解（15 個檔案）全部改寫成目前實際成立的說明，README 修正 6 處與程式碼不符之處（其中預算上限仍寫 US$0.30，實際已是 $0.80）。

**C0（缺陷修正，不算重構）**：分析中發現 `_analyze_worker()` 在自己的 try 之外做了五件可能拋例外的事（`get_client()` 在缺 API 金鑰時會直接拋），一旦拋出就不會送出終端事件，job_manager 的 pump thread 會永遠停在 `queue.get()`、分析 slot 永不釋放，**之後每一支影片都卡在 queued，只能重啟伺服器**。因為是行為變更所以獨立一個 commit：worker 拆成兩層保證一定送出剛好一個終端事件，pump 的釋放 slot 移進 `finally`。

**驗證方式**：除了全套測試，每個結構性步驟都做了新舊實作的等價比對——`analyzer` 重播完整 worker 比對事件序列／狀態寫入／DB 呼叫／總花費（正常與預算截斷兩條路徑）；`search` 用 9 組查詢（含否定句、泛用詞、指定影片、top_k 截斷）逐欄位比對；模態旗標在真實 `app.db` 上比對 10 支影片。最後三個 commit 在提交前各自匯出成獨立副本跑過完整測試，確認**單獨 checkout 每個 commit 都是綠的**——這個做法也因此抓到兩個原本測試裡的錯誤（`monkeypatch.undo()` 連 fixture 的 `db.DB_PATH` 一起撤掉，因為主目錄剛好有 `app.db` 而一路綠燈）。

**刻意不做**：不引入 Repository／DI container／CQRS（目前規模下 15 個 `db.*` 直呼更好讀）；不移除 `video_service` 的 11 個一行透傳（刪掉會讓 API 層直接依賴 db，方向更差）；`progress_estimation` 不改用 executor（它的 worker 是 `daemon=True`，換掉會讓分析途中 Ctrl-C 要等 ffmpeg／Whisper 跑完）；不修正本地 OCR 失敗時已花費用被丟棄的既有低估（那是行為不是結構債，已在程式碼註解標記）。

完整的任務看板（含每張卡的驗證方式、刻意不做的理由，以及過程中做錯／走錯的記錄）見 [`refactor-board.html`](refactor-board.html)。

## 2026-08-27：資料庫從 SQLite 遷移到 PostgreSQL

完整計畫、決定理由與執行紀錄見 [`14-postgresql-migration-plan.md`](14-postgresql-migration-plan.md)，
逐階段進度看板見 [`pg-migration-board.html`](pg-migration-board.html)。這裡只記時間軸摘要。

**動機不是效能**：22 支影片／931 個片段，SQLite 完全夠用。真正的理由有兩個——專題發表需要
一個能講的技術主題，以及為之後上 pgvector 鋪路。這點在計畫文件裡寫明，沒有包裝成效能優化。

**條件很好**：`db/` 是全專案唯一碰 SQL 的地方（`db/` 以外沒有任何 `sqlite3` import 或查詢語句），
所以 `services/`／`pipeline/`／`api/` 三層**一行都沒有因為換資料庫而改動**。沒有 ORM 要重寫、
沒有 migration 歷史要轉換。

**技術選型**：Docker 跑 `pgvector/pgvector:pg17`（port 5433 避開機器上另一份 PostgreSQL）、
`psycopg` 3 搭配手寫 SQL（不引入 SQLAlchemy／Alembic——`db/` 已經是乾淨邊界，改 ORM 是另一個
獨立專案，綁在一起會讓「搜尋結果變了」無法歸因）、embedding 維持 `BYTEA` 不換成 `vector` 型別
（pgvector extension 有裝好，但欄位型別留給之後獨立的一步）。

**最大的收穫是刪掉東西**：FTS5 虛擬表換成 `segments.content` 這個 generated column ＋ `pg_trgm`
GIN 索引之後，`backfill_fts()`／`prune_orphan_fts()`／`delete_for_video()` 的 FTS 同步／
`insert_segment()` 的第二次寫入四段程式碼全部消失，連同 `migrate_columns()` 與兩支
`_row_to_record()` 裡 9 處 `if "x" in keys` 防呆——`db/` 從 1348 行降到 1231 行。
更重要的是根除了一整類 bug：FTS5 的 rowid 靠呼叫端自己同步，漏掉就留下殘留列，實測曾有
**925/1795（52%）**是對不到片段的殘留列，佔掉 bm25 前 200 名額、把真正命中的片段擠出候選集。
generated column 由資料庫維護，這種脫節在結構上不可能發生。

**檢索的替代方案**：PostgreSQL 沒有 FTS5，`to_tsvector` 對中文有一樣的斷詞問題，所以同樣走
trigram 路線，BM25 分數在 SQL 裡自己算（k1=1.2、b=0.75 對齊 FTS5 預設值，分數加負號維持
「越小越相關」的既有介面契約）。保住 IDF 是重點——`sparse.py` 的短詞比例門檻整套建立在
「長詞有真實 IDF 加權」的前提上。

**驗收**：動工前先在 SQLite 上跑一次 golden set 存 baseline（切換後就沒有 SQLite 環境可比了），
遷移後跑同一份 18 題對照：

| 指標 | SQLite | PostgreSQL |
|---|---|---|
| Recall@1／Recall@5／nDCG@5／IoU／No-answer F1 | — | **完全相同** |
| MRR | 0.5085 | 0.5077（−0.0009） |

那 0.0009 沒有用「在誤差內」帶過：逐題比對後確認**只有 gs-012 一題**的正解從第 9 名掉到
第 10 名，13 道可回答題目平均下來正好是這個數字，而 9 和 10 都在 top-5 之外。再進一步做了
不含 LLM 的隔離比對（相同取詞分別打 SQLite FTS5 與 PostgreSQL），確認**召回集合完全一致**
（26 vs 26、93 vs 93），差異只在同一批候選集內部的排序——兩套 BM25 實作的預期落差。

資料搬遷保留原 id（golden set 與既有對話都直接引用），2338 個向量／9,576,448 bytes 逐位元組
比對相符。實跑 app 走完八個流程（讀取／搜尋／多輪對話／狀態持久化／上傳分析／重新分析／刪除／
YouTube 下載）共 117 個請求、0 個錯誤。測試從 336 支增加到 337 支、全數通過，隔離方式從
「每測試一個臨時 SQLite 檔案」換成「共用 `avs_test` 資料庫 ＋ 每測試 TRUNCATE」，並加了
一道「資料庫名稱必須以 `_test` 結尾才准 TRUNCATE」的防護——正式資料庫現在裝著真實分析結果，
一次 DSN 組法的錯誤就是無聲的資料全毀。

**順手修掉兩個 SQLite 時期就存在、只是沒被觸發的問題**：查詢字串裡的 `%` 沒有跳脫（會變成
「比對任意字串」、一次撈出全部片段），以及 `fts_like_search()` 的 `LIMIT` 沒有 `ORDER BY`
（PostgreSQL 不保證回傳哪幾列，而呼叫端要拿結果算比例門檻）。

## 2026-08-29：影片庫的主題分類與庫內搜尋

參考 YouTube 首頁的「搜尋列＋主題 chips」（`YT_01.png`），在「影片庫」頁籤加上主題分類與庫內搜尋。
完整記錄見 [`11-web-ui-warm-redesign-plan.md`](11-web-ui-warm-redesign-plan.md) §8.17。

**選了最便宜的那條路**：分類用**關鍵字規則**從「標題＋摘要」推導，固定 10 類，整件事就是前端一個
新檔 `lib/videoCategory.ts`——**不改後端、不改資料庫、不呼叫 LLM、不花任何 API 成本**。AI 自動分類
是被權衡掉的，不是不可行（摘要已經存在，23 支合計不到 US$0.01），但它要加欄位、要回填、analyzer
要多一次呼叫；日後要換過去的改動面也很小：`classifyVideo()` 換成讀後端回傳的欄位，UI 一行不動。

**字典是對著真實資料調出來的，不是憑空寫的**。先用一次性腳本連 PostgreSQL 把 23 支已分析影片跑過
一輪，調了兩輪後 **23／23 全部分對、0 支落到「其他」**：第一版把類別叫「程式與教學」，害
`100 Animals in Chinese` 這種語言教育影片被類別名本身排除；另外收掉四個過鬆的關鍵字
（`skills`／`goal`／`名稱`／`bmw`），拿掉後仍是 23／23，**證明它們沒有貢獻、只帶來誤判風險**。

**搜尋是庫內篩選，不是把 §8.6 的決定推翻**：§8.6 剛移除過影片庫的搜尋列，但那條是「把字帶去
`/search` 做語意檢索片段」的捷徑；這條只比對已經在手上的標題與摘要，邊打邊篩、不打 API、不跳頁。
要守的規則是「**語意搜尋只有『搜尋影片』頁一個入口**」，沒有被破壞——也因此否決了「找不到結果時
給一個按鈕跳去語意搜尋」的提案。

Playwright 實跑 32 項全過（chips 分佈與事前驗證完全一致、「半導體」靠摘要命中 2 支標題沒有這三個
字的影片、chips 數量不隨打字跳動、四種空狀態文案、390px 無溢位、零 console error）。

**已知天花板**：字典就是上限，題材差很多的新影片會一路掉進「其他」，直到有人補關鍵字。判斷「該補
了」的訊號很明確——「其他」那顆 chip 的數量開始追上其他類別。

## 2026-08-29：搜尋範圍支援多選影片

搜尋範圍從「全部影片／單一影片」放寬成**任意一批已分析影片**。決策背景與實測數據見
[`02-technical-decisions.md`](02-technical-decisions.md#搜尋範圍從全部單一影片放寬到任意子集)，
行為規格見 [`12-search-query-logic.md`](12-search-query-logic.md) §2／階段 1／階段 4。

**五個定案決策**：入口放在影片庫（每列勾選＋底部「在選取影片內搜尋」，單支的「在此影片內搜尋」
變成「勾一支」的捷徑）；有指定範圍就**不套用影片層級篩選**（選了就全查，跟單支的舊行為一致）；
對話搜尋**共用同一份範圍**；BM25 的範圍下推**單選多選一起修**；UI 勾選的範圍對 LLM 是**硬邊界**。

**真正的技術重點是順手挖出來的既有缺陷，不是型別從 `int` 改成 `int[]`**。sparse channel 的 SQL
完全沒有 `video_id` 條件——它在**全庫**取 BM25 前 200 名，才由 Python 端用範圍過濾。而 `LIMIT`
是排序之後才截斷的，所以限定範圍搜尋時範圍外的片段會先把名額佔走，sparse channel 整個落空、
RRF 只剩 dense 一路、`is_confident` 恆為 false。**這個缺陷單支影片的舊行為就有**，多選只是讓它更
容易觸發。解法是在 `_BM25_SQL` 前面加一個 `scope` CTE；`video_ids` 為 `NULL` 時語意逐字不變。

踩到兩個 PostgreSQL 的坑：`scope` 被引用兩次，預設會被**物化**、`content` 的 pg_trgm GIN 索引就
吃不到，必須標 `NOT MATERIALIZED`；`stats` 也要讀 `scope`，只縮 `df`／`hits` 會讓 IDF 的分母還是
全庫文件數、分數整個灌水。

**對話搜尋的硬邊界規則**：LLM 解析出的範圍只能在使用者勾選的範圍內**再收窄**（取交集），不能擴張
出去；交集為空（LLM 認錯影片）就整個忽略這次收窄、退回勾選的範圍，而不是回零筆。理由是勾選是明確
的使用者操作——畫面上勾著 3 支、實際卻搜了第 4 支，使用者沒有任何線索可以除錯。收窄了會把實際
生效的範圍回傳給前端（`ConversationTurnOut.video_ids`）並顯示在狀態列。範圍由前端**每輪重送**、
刻意不存進 `conversations` 表：它屬於「使用者現在看的畫面」，存起來的話在影片庫改了勾選、回到對話
還會沿用舊範圍。

**前端改用共用 context 而不是 URL 參數**：舊做法是 `/search?video_id=…&video_title=…`，但範圍現在
要給「搜尋影片」與「對話搜尋」兩頁吃，兩頁各自從 URL 解析一定會分岔。改成
`lib/useSearchScope.ts`（只存 id，標題從 react-query 的 `['videos','library']` 快取查，跟影片庫同
一個 query key、不會多打 API）。`VideoListItem` **一行都不用改**——它的 checkbox 本來就是「有傳
`onCheckedChange` 才 render」，影片庫補傳 props 就長出來了。

**實跑驗證**（Playwright 驅動真實 app）：勾 2 支 → request body `video_ids:[28,8]` → 15 筆結果
全部只來自那 2 支、無範圍外洩漏 → 移一顆 chip 變 1 支 → 切到對話頁範圍相同 → 切回來範圍與結果
都還在（keep-alive）→ 零 console error。另跑一次真實對話輪次（`video_ids:[8]`），6 筆結果全來自
video 8、回傳的生效範圍是 `[8]`。**top1 融合分數 0.25**，遠高於「只有 dense 命中」的上限 0.1667，
證明 sparse channel 真的活著。**成本**：同句查詢全域 US$0.00016、限定範圍 US$0.00004。

**刻意沒做**：`search_log` 不加範圍欄位。它現在的契約是「使用者原始 query＋花費」，加欄位要一併
決定歷史列怎麼填、範圍算不算稽核軌跡的一部分，跟這次的功能無關。

**已知天花板**：範圍下推只解決「限定範圍」的情形，**全域搜尋的 200 名額截斷還在**。而且限定範圍
這條路徑**從來沒進過 golden set 評測**（`evaluation.py` 不傳範圍參數，17 題全是全域搜尋），所以
「選了 N 支之後的準確率」改動前後都是未知數；反過來說全域路徑的 SQL 語意逐字未變，既有 baseline
沒有失效、不需要重跑。

## 2026-08-29：把影片內容整理成一份結構化文件

補上「摘要」與「單一片段」之間缺的那一層：整支影片的素材整理成一份可交付的文件——工廠影片產出
生產流程 SOP、烹飪影片產出教學步驟、課程產出課堂筆記。決策背景與實測數據見
[`02-technical-decisions.md`](02-technical-decisions.md#影片內容整理成文件)。

**規劃階段先查真實資料庫，結果直接改掉了設計**。使用者舉的兩個範例，素材結構正好相反：工廠影片
（video 31）的流程知識全在**字幕**、畫面描述是雜訊；烹飪影片（video 13）反過來——字幕是 Whisper
在純音樂上產生的**幻覺俄文**（`Девочка-пай`、`Редактор субтитров А.Семкин`），流程全在畫面。
加上覆蓋率（無畫面描述 1/1,156、無字幕 150/1,156），得到 prompt 的三條硬要求：每步必須有時間戳、
**字幕與畫面矛盾時以畫面為準**、不適合就選 `content_log` 不要硬掰。

**跟摘要最大的差別是用了 `ocr_text`**。那個欄位覆蓋率 93%（1,076/1,156），`summary.py` 完全沒碰。
壽司那支證明它是決定性的：產出的文件裡「上方保留 3 公分」「靜置 10 分鐘讓壽司釋放」逐字來自畫面
字卡——那支字幕全壞、畫面描述只說得出「捲起來」，不帶 OCR 會產出一份沒有份量也沒有時間的空洞
食譜。組 prompt 時順手發現 **21 個片段的 `ocr_text` 是字面字串 `"null"`**，濾掉但沒回填資料庫。

**刻意不抄摘要的 `segments[:200]` 硬截斷**：摘要截掉尾段只是不完整，SOP 截掉尾段會默默少掉最後
幾個製程步驟，比直接失敗更糟。實測最大 112 段、1 小時上限也只到約 360 段，context 放得下。

**第一版被敘事形式騙走**。實跑時 video 31 被判成 `content_log` 而不是 `sop`——內容完全正確（章節
就叫「主板生產線」，步驟是塗矽膏 → 貼片機 → 測試 → 包裝），只有型別錯了，因為那支是第一人稱參觀
敘事（「我是翼王，這次來帶大家參觀」），模型看形式不看內容。prompt 補一條「`content_log` 是最後
退路，判斷看內容不看敘事形式」之後，四種類型全部判對，而且球賽那支**沒有被過度矯正**成硬掰的
打擊 SOP。

**兩個估計都估錯了，而且是往好的方向**：規劃時估成本 US$0.005/份、耗時 20～40 秒；實測成本
**US$0.0004～0.0026**（5／33／65 個片段的三支），耗時 **7.5 秒**。所以維持同步 REST、沒有開第三種
job type 是對的——那會踩到 `retry_job()` 讓新 type 靜靜掉進 download 分支的既有地雷。

**加回一個最小的 schema migration**。PostgreSQL 遷移時 `migrate_columns()` 被整個移除，理由是
「全新資料庫、一次定義齊全」。這次加三個欄位證明那個前提只在遷移當下成立：`CREATE TABLE IF NOT
EXISTS` 對既有資料庫是 no-op，`_row_to_record()` 直接 `KeyError`——實測就是這樣讓 14 個測試同時
掛掉的。`create_table()` 現在多三行冪等的 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，不需要任何
人手動下 SQL。

Playwright 實跑：四顆按鈕、「摘要／整理文件」頁籤共用同一塊捲動區、既有文件正確載入（只打 GET、
沒有誤觸重新產生）、時間戳靠右對齊、零 console error。

**已知天花板**：**文件品質沒有任何量化方式**——搜尋有 golden set，這個只能人工看，代表之後改
prompt 沒有回歸測試可擋。幻覺步驟的風險只是被緩解（時間戳強制 + uncovered 欄位），4 支的樣本不是
保證。步驟的時間順序完全靠模型自己排，實測 video 29 出現過 `[00:48]` 排在 `[00:38]` 前面。

## 2026-08-29：摘要與整理文件合而為一，移除詳細面板的縮圖

「整理成文件」上線後實際用起來才看清楚兩個問題：文件的 `overview` 跟「摘要」在講同一件事，卻要按
兩顆按鈕、各花一次 LLM 呼叫、切兩個頁籤；而最上方那張大縮圖是純裝飾（面板裡沒有播放器，點了不會
播），卻吃掉 `md:max-h-[42vh]`——一份 SOP 有二三十個步驟，最缺的就是垂直空間。決策細節見
[`02-technical-decisions.md`](02-technical-decisions.md#摘要與整理文件合併成一個動作)。

**動手前先確認 `videos.summary` 能不能刪，答案是不能**。它有三個消費端，都不是顯示用：全域搜尋的
影片層級相關度篩選拿它去 embed（`search/dense.py:87`）、影片庫主題分類 chips 的關鍵字比對、庫內
搜尋比對標題＋摘要（`lib/videoCategory.ts`）。所以合併只能發生在介面與操作層，資料層要繼續寫入。

**做法是讓文件的 `overview` 一稿兩用**：同一次 LLM 呼叫的產出同時寫進 `videos.summary`，一顆
「整理成文件」按鈕更新兩者。**刻意不新增 `video_summary` 欄位、也不改名**——改動當下已經有 8 支
影片存了文件，改欄位名會讓那些存量 JSON 全部 `ValidationError`；而給新欄位設 pydantic 預設值又會
讓它從 OpenAI structured output 的 `required` 掉出去，strict 模式會拒絕。所以只改 prompt 對
`overview` 的要求（從「說明這份文件涵蓋什麼」改成「說明**這支影片**在講什麼」、禁止「本文件」
開頭），存量文件的結構一個位元都沒動。

**成本只能算一次**：`update_video_document()` 多收一個 `summary` 參數，在同一句 UPDATE 裡把摘要與
文件一起設。拆成兩次呼叫會讓同一次 LLM 呼叫的成本被累加兩次——這是這次最容易寫錯、也特地補了
測試鎖住的地方。

實跑 video 13（壽司）驗證：摘要語氣正確變成「這支影片教觀眾如何在不使用竹簾的情況下自製壽司…」
而不是「本文件…」，`document.overview == videos.summary`，`cost_usd` 只增加 **US$0.00044**（一份
文件的量，沒有重複計費），全域搜尋仍正確收斂到這支影片。Playwright 實跑：詳細面板的 `<img>` 數量
歸零、頁籤消失、按鈕剩三顆、390px 無溢位、零 console error。

**保留沒刪的**：`pipeline/summary.py` 與 analyzer Phase F 的自動摘要完全不動（新影片分析完仍會自動
有摘要）；`POST /videos/{id}/summary` 端點與測試留著、只是前端不再呼叫，照 `POST /videos/upload`
的既有先例。

**已知取捨**：8 支已有文件的影片，摘要仍是分析時產生的舊版本，要等下次按「整理成文件」才會被
覆蓋。兩種摘要都合格，沒有急迫性，所以沒有為了統一而花錢重跑。

## 2026-08-29～30：第四輪重構

### 過程中被推翻的三件事

2. **我寫的註解宣稱了一個不存在的因果**。`useJobSettlement` 裡我寫「先記錄再呼叫 callback，否則 setState 會讓 effect 重跑、同一批收尾兩次」——把兩行調換過來 22 支全過。順序保留（讓不變式跟 callback 做什麼無關），但註解改成講真話。這是第三輪 P2 的同一個教訓。

## 2026-08-30：點文件的時間戳直接播放該段影片

「整理成文件」產出的每個步驟都帶 `timestamp_sec`，但它一直只是個純文字標籤。這次讓它可以點——點下去影片就從那一秒開始播。

**後端零改動**：`GET /videos/{id}/stream` 用的 Starlette `FileResponse` 本來就回 `accept-ranges: bytes`，實測帶 `Range` 會回 **206 Partial Content**，所以跳時間點是真的 seek，不是把整支影片下載完再跳。`VideoPlayer` 元件也早就處理好「同一支影片內換片段直接改 `currentTime`、換影片才重新載入」。真正要決定的只有一件事：播放器擺哪裡。

**播放器點了才出現，而且可以關掉**。這個面板的滿版縮圖是前一次（`f06bd8a`）才刻意移除的，理由是「純裝飾卻吃掉 42vh，而一份 SOP 有二三十個步驟，最缺的就是垂直空間」。常駐播放器會把那個問題原封不動帶回來，所以改成使用者主動要看才給、看完可以收掉；播放器高度也上限在 `32vh`，下面的步驟一直看得到。放在捲動區外面而不是 sticky 在裡面，是順著面板既有的「上面全是 `shrink-0`、內容區吃剩下的高度」結構做，不用處理 z-index 與蓋住摘要的問題。

**`seekKey` 是為了一個不加就會漏掉的情況**：`playAt` 已經是 12 秒時再點同一個步驟，`setState` 的值沒變，React 不重繪，`VideoPlayer` 的 effect deps 也就沒變——使用者手動把進度拖走之後想「回到這一步」會完全沒反應。所以 `VideoPlayer` 多一個選用的 `seekKey`（每次點擊遞增），呼叫端不傳就完全維持原本行為（搜尋頁與對話頁每次選的都是不同片段，沒有這個需求）。

**測試需要一支真的影片**。種子資料的 `file_path` 原本全部指向不存在的檔案（smoke 不播放影片），但那樣 `onLoadedMetadata` 不會觸發、seek 也就不會發生，e2e 只驗得到「播放器出現了」而驗不到重點。所以 `seed_smoke_db.py` 會用 ffmpeg 現場產一支 30 秒的迷你影片（320x180 純色、每秒一個關鍵影格讓 seek 落點精確），放在 gitignore 過的 `video/smoke/`。5 支 e2e 因此能斷言 `video.currentTime` 真的落在目標秒數。

**真實資料驗證抓到一個合成測試看不到的情況**：真實文件裡**兩個步驟可能共用同一個時間戳**（Python 教學那支有兩步都是 23 秒），只用秒數當 `aria-label` 的話，螢幕閱讀器會聽到兩個一模一樣的按鈕名稱、分不出是哪一步。改成帶上步驟標題（`從 00:23 開始播放：下載 Python`）。

用正式資料庫實跑驗證：點「00:23」→ `currentTime=23.00s`（影片全長 171 秒）並開始播放；再點另一個時間戳 → `currentTime` 跟著換而 `src` 沒變（是 seek 不是重載）；關掉播放器 → `<video>` 消失、步驟回到滿版；全程零 console 錯誤。

### 後續發現：模型會產生對不上影片的時間戳

功能上線後把 8 支已整理文件全部量了一次，結果比預期糟：**3 支（38%）有超出影片長度的時間戳**（`How Intel Builds...` 影片 18:33、步驟寫到 22:56；技嘉那支 6:11、寫到 9:03；`100 Most Beautiful Faces` 10:02、最後兩步寫 15:10／15:40），另有 **2 支（25%）步驟時間戳倒退**。

這推翻了 `document.py` 原本的一個宣稱。那裡寫著「時間戳是必填的，這是防幻覺的主要手段：講不出『這是影片第幾秒的內容』的步驟，通常就是模型自己補出來的」——前半仍然成立，但**反過來不成立**：模型講得出時間戳，那一步也還是可能是編造的。註解與 `docs/02` 的對應段落都改成講這件事。

值得記的是**為什麼現在才發現**：時間戳只是純文字時，沒有人會去核對它跟影片長度的關係；做成可以點之後，點下去跳到影片結尾，問題立刻現形。功能沒有製造這個 bug，是讓既有的資料品質問題變得看得見。

處理方式（產生時夾住／前端擋住／重排順序）三種各有取捨，**刻意先不做**——三者都會改動既有 8 支文件的呈現，需要先決定要哪一種，見 [`05-known-limitations-and-open-items.md`](05-known-limitations-and-open-items.md) 的待辦。

### 改成觀看模式：影片左、文件右

第一版把播放器就地展開在摘要上方、限高 32vh、可關閉——理由是保護垂直空間（詳細面板只有半版寬，而一份 SOP 有二三十個步驟）。實際用起來的問題是**兩件事都做不好**：影片小，文件也被擠掉。

改成給影片一個自己的畫面，版面對齊 YouTube 觀看頁：點時間戳 → 影片庫的清單收起來，左邊播放器（約 2/3 寬）、右邊摘要與文件（1/3），左上角「返回影片庫」。**右欄的時間戳仍然可點**——這正是這個版面的用途，邊看邊跳下一步，不必退回清單再點一次。原本的限高播放器整塊移除。

三個做法裡選了「影片庫頁面內的模式切換」，不是新路由也不是全螢幕彈窗：`App.tsx` 的頁籤是**精確路徑比對**（`p.path === pathname`，不符就導回 `/youtube`），巢狀路由得動到 keep-alive 的核心；全螢幕彈窗則會蓋掉 Header 的頁籤導覽，讓這一頁變成全站唯一的例外——而 P_03 那張 YouTube 觀看頁的頂部導覽也是留著的。觀看狀態只放在元件 state、**沒有同步到網址**：頁籤是 keep-alive 的，少了網址只影響「可分享」與「上一頁退出」，而 `SearchPage` 為了 `?q=` 寫的那段 `consumedParams` 說明了在 keep-alive 下處理網址參數的成本，留成獨立的一步。

摘要與文件抽成 `VideoSummaryAndDocument` 給兩個版面共用（文件查詢的 query key 相同，所以共用快取、不會多打 API）。觀看模式**刻意不放**「在此影片內搜尋／整理成文件／重新分析」三顆按鈕：那是影片庫的管理動作，觀看時用不到還佔空間。

**兩個實跑才發現的問題**：

1. 播放器原本用 `flex-1` 撐滿欄高，結果 917×715 的框裝 16:9 影片，上下各留約 100px 黑邊。改成 `aspect-video` 依寬度定尺寸（917×516，正好 16:9）。
2. 窄螢幕（390px）版面上下堆疊，**點下方文件裡的時間戳後，播放器在畫面外的上方**——影片開始播了卻看不到。加上 `scrollIntoView`。補測試時發現第一版測試點的是第 2 個步驟、位置還在視野內，拿掉修正照樣綠；把 stub 文件加長到 6 個步驟、改點最後一個，測試才真的咬得住。

### 超出影片長度的時間戳不給點

承上一節量到的資料（8 支文件裡 3 支有超出影片長度的時間戳）。觀看模式上線後這個問題變得刺眼——在佔 2/3 畫面的播放器上點到那種時間戳，會直接被丟到影片末尾。

三個選項裡選了**前端擋住**：超出長度的時間戳停用（刪除線＋灰字＋tooltip），並在文件開頭用一句話講出「有 N 個步驟的時間點超出影片長度（MM:SS），已停用它們的播放連結」。**不只靠 tooltip**——滑鼠移過去才看得到的說明，等於只有已經起疑的人才會發現。

停用的樣式刻意跟可點的時間戳同一種外觀語言（一樣是 `<button>`，只是變灰加刪除線），使用者看得出「這裡本來應該可以點」，而不是以為這一步比較不重要。

容許 2 秒誤差：`videos.duration_sec` 是整數，真實長度可能多零點幾秒，嚴格比較會把剛好落在片尾的合法步驟誤判。2 秒吸收得掉這個誤差，又不會放過真正的問題——有問題的那 3 支超出幅度分別是 4 分 23 秒、2 分 52 秒、5 分 38 秒，全是分鐘級的。

另外兩個選項刻意沒做：**產生時就夾住**會默默改掉模型的輸出，**重排順序**只解決「倒退」不解決「超出長度」，而且會打散模型刻意的章節分組。

**這是呈現層的緩解，不是修好資料**——那幾步的內容本身仍然可疑（時間點都編得出來，內容多半也是），所以提示裡明講「內容本身也請斟酌」。

實跑技嘉板卡工廠那支（影片 6:11、文件寫到 9:03）驗證：18 個時間戳可點、1 個停用，提示正確顯示影片長度 06:11，零 console 錯誤。

### 追查「BMW 那支的 SOP 為什麼只有 8 步」，結果推翻了上一節的歸因

使用者問 BMW 工廠那支（17:43、104 個片段）的 SOP 為什麼只有 8 個步驟。查下去發現**兩個獨立成因**，而其中一個推翻了上一節剛寫下的解釋。

**成因一：字幕整支都是 Whisper 幻覺。** 97 個有字幕的片段裡 **95 個（98%）是同一句 `Thank you for watching.`**（純環境音影片的典型幻覺）。三個素材欄位裡字幕整欄是雜訊，模型只能靠高度雷同的工廠畫面描述工作。

值得記的是**專案早就有兩道幻覺過濾，而且模式 A 抓到了**（76/97 個片段 `no_speech_prob` > 0.7）——但那道判斷只決定「要不要建 embedding」，`segments.transcript` 照樣寫入原始輸出，而 `build_material()` 直接讀它、不看 `no_speech_prob`。**搜尋端受保護，文件產生端沒有。** 模式 B 則是結構上構不到：它看單一詞佔比，而這裡重複的是整句（`thank` 只佔 0.25，門檻 0.5）。

**成因二（更重要）：時間戳塌掉不是模型幻覺，是我們自己的素材格式。** 素材給 `[MM:SS]`，但 schema 的欄位叫 `timestamp_sec`（秒）——等於逼模型換算，而它常常直接把 `[03:18]` 的 `18` 抄過去。這一個不一致同時造成兩種症狀：**塌在 60 秒內**（BMW 8 步全在 00:52 內）與**超出影片長度**（Intel 18:33 寫出 22:56）。

**這推翻了前兩節。** 我在 `08f5d25` 把它記成「模型講得出時間戳也可能是編造的」，還在 `9171d98` 做了前端擋住。歸因是錯的——前端擋住仍然留著當安全網，但它從主要對策降級成保險。

**驗證方式**：三次單變數實驗（每次約 US$0.002，唯讀不寫庫）。實驗一濾掉幻覺字幕 → BMW 步驟 8→12，**但時間戳仍全塌在 00:56 內**（證明兩個成因獨立）。實驗二只改時間戳格式 → 時間戳散到 08:42。實驗三在 Python 與 Intel 上重複 → 一致。

**修法**：素材同時給 `MM:SS` 與總秒數（`[03:18｜198 秒]`），prompt 明講「直接填方括號裡的秒數，不要自己換算」。順帶修掉另一個素材缺陷——`_clean()` 把欄位內的換行壓成空白，讓 prompt 開頭宣告的「每行是一個片段」成真（原本每支影片都有 28%～88% 的行沒有時間戳前綴，線性代數那支 461/526）。

**9 支文件全部重跑**（US$0.0148，事前備份到 scratchpad，因為文件重整沒有版本歷史）：

| 指標 | 前 → 後 |
|---|---|
| 超出影片長度的步驟 | **4 → 0**（9 支全清） |
| 時間戳涵蓋率（最差的兩支） | BMW 5%→80%、Python 18%→93% |
| 涵蓋率略降 | 龍隊 31%→25%、線性代數 74%→57% |
| 步驟數 | 有增有減（技嘉 19→12、Python 7→14） |

**沒有全面改善，也不假裝有**：步驟數與涵蓋率有增有減，單次重跑分不出訊號與雜訊；我先前 n=1 實驗看到的步驟數改善沒有可靠重現。唯一乾淨清掉的是「超出影片長度」。另外「步驟倒退」這個指標本身有問題——它把整份文件攤平比大小，會把「章節依主題分、時間軸互相重疊」也算成倒退（Intel 的「自動化生產線」02:09~15:30 與「測試與質量檢查」11:45~18:01 就是這種），真正的亂序只剩章節內的個位數。

**仍未處理**：幻覺字幕還是會進文件素材（成因一）。那需要 `build_material()` 拿得到 `no_speech_prob`，是另一件事。

### 補完成因一：幻覺字幕的過濾，而上一節預告的修法是錯的

上一節收在「那需要 `build_material()` 拿得到 `no_speech_prob`」。**接著做的時候發現那個方向不對。**

`no_speech_prob` 是逐片段的信心分數，而幻覺字幕的特徵是「整支影片一直重複同一句」。拿全庫量過就看得出它接不上：BMW 那支它抓到 76/97，但同樣整欄是幻覺的 Intel（`... ... ...` 佔 65%）只抓到 **2/108**、video 6（佔 74%）只抓到 **1/82**；反過來線性代數那支是真實講課，卻有 16 段被它標記。**上一節之所以以為它可用，是因為只在 BMW 一支上看過。**

**改用影片層級的重複比例**，在 `build_material()` 內算：最常出現的那一句佔全部字幕的比例超過 0.4，整欄丟掉。全庫 23 支的分布乾淨可分——

| | 單一句佔比 |
|---|---|
| 未觸發（真實語音／混合） | 1%～**26%**（最高是 video 1） |
| 觸發（整欄幻覺） | **65%**～79%（Intel 65、BMW 72、video 6 74、Intel-28 75、video 5 79） |

中間 26%～65% 是空的，門檻放哪裡都一樣。

**OCR 刻意用不同策略**：只丟重複的那個字串、不丟整欄——BMW 的 `ocr_text` 裡有 67 句各自不同的製程旁白（`Once the BIW REACHES THE COMPONENT ASSEMBLY LINE…`），那才是這支影片的主要訊號，整欄丟掉等於把僅有的內容也丟了。門檻 0.15，實測抓到的全是頻道浮水印：`FRAME`（BMW／Intel）、`CPBL TV`（龍隊）、`SPORTS HD`／`FA3NHD`（Messi），零誤殺（浮水印 21%～47%、真實內容最高 12%）。

**驗收先做不花錢的那半**：23 支全部跑一次判定，比對事前從資料分布標好的預期。22/23 相符，唯一不符的是壽司那支——它只有 3 句字幕，低於 `_MIN_SAMPLES_FOR_JUNK_CHECK = 8` 所以不判定。那是刻意的：3 句裡剛好重複 2 句就湊得出 67%，是樣本雜訊不是幻覺訊號，寧可漏也不要誤殺。

**再花 US$0.0019 重產 BMW 的文件**（事前備份，文件重整沒有版本歷史）：

| 指標 | 前 → 後 |
|---|---|
| 步驟數 | **7 → 12** |
| 時間戳範圍 | 16s～864s → **16s～1041s**（片長 1063s） |
| 涵蓋率 | 81% → **98%** |
| 超出片長／順序倒退 | 0／0（維持） |
| 素材長度 | 20,299 → 15,062 字元（-26%） |

**爆炸半徑**：文件那一側 23 支裡 8 支的素材有變、15 支逐字不變；摘要那一側 5 支有變（BMW -40%）。摘要端也一起吃到過濾是刻意的——兩邊本來就餵同一批髒資料。

**這次的教訓跟上一節同一個形狀**：n=1 的觀察會給出看似合理但錯的歸因。上一節是「模型幻覺」（實為素材格式），這一節是「接上模式 A 就好」（實為工具選錯）。兩次都是把全庫 23 支攤開量過才看出來，而那個量測不花 API 錢。

### 分析完就有文件：Phase F 從「產生摘要」改成「整理文件」

使用者要求「分析影片產出摘要時，也同時產生整理成文件的內容」。查下去發現這件事在程式碼裡已經半路做完了，剩下的是把它接起來。

**接起來之前的狀態**：`videos.summary` 有兩個來源——分析時的 Phase F（`summary.py`，100～200 字純文字）與使用者按「整理成文件」（`document.py` 的 `overview` 一稿兩用）。後者會覆蓋前者。也就是說**我們已經認定 `overview` 才是正本**（前端連「重新產生摘要」那顆按鈕都拿掉了），卻還是讓每支影片先花一次錢產一份注定被覆蓋的摘要，而真正有價值的文件要使用者自己想到去按。

**做法**：Phase F 改成先呼叫 `document.generate_document()`，摘要當它的副產品；**文件失敗才退回 `summary.generate_summary()`**。

退路不是保險起見加的。`videos.summary` 不只是顯示欄位——搜尋的影片層級篩選（`pipeline/search/dense.py`）與影片庫的主題分類、庫內搜尋（`lib/videoCategory.ts`）都在讀它。文件失敗就整支沒摘要的話，那支影片會在搜尋端被降權，比「文件沒整理出來」嚴重得多。

**兩個容易踩的坑，都跟「同一次呼叫的錢算幾次」有關**：

1. 手動整理文件走 `db.update_video_document()`，它的 `cost_usd` 是**增量累加**；分析流程走 `db.mark_video_analyzed()`，它的 `cost_usd` 是 analyzer 算好的**絕對總額**（文件花費已經透過 `ctx.spend()` 進去了）。所以文件三欄要跟著 `mark_video_analyzed()` 一起寫、不能順手改呼叫 `update_video_document()`——兩支都呼叫的話同一份文件會被計費兩次。三欄都用 `COALESCE(%s, ...)`：重新分析但這次文件失敗時，舊文件留著比清空好。
2. 前端文件那支 query 是 `staleTime: Infinity`（原本文件只有按按鈕才會變，按鈕自己 `setQueryData`）。重新分析現在也會換掉文件，不多失效一個 `videoDocumentKey` 的話，畫面會繼續顯示上一輪的文件——而裡面的時間戳指向的是已經被 `_write_segments()` 換掉的舊片段。

**順帶修掉一個既有的洞**：`db.reset_to_pending()` 清 `summary` 卻不清文件三欄，留下一份指向已刪片段的文件。文件只能手動整理時這是少見情況，Phase F 自動整理之後每支重置的影片都會遇到。

**驗收**：426 個單元測試通過（新增 8 支：Phase F 的四條分支——成功／文件失敗退回摘要／兩條都失敗／超支跳過——加上 `mark_video_analyzed()` 的文件欄位與 `reset_to_pending()` 的清除）；`tsc -b`／`oxlint` 乾淨。整合測試（`-m integration`，真的花錢跑一支合成影片）加了「分析完 `document_json` 要有值」的斷言，空的代表走了退路，會轉紅而不是默默通過。

**沒做、也講清楚為什麼**：文件成本仍然併進 `videos.cost_usd`，沒有獨立欄位——這一條本來就在待辦清單上，而且自動整理之後那個數字更難拆了。存量影片也不會自動補文件，只影響之後才分析的影片。

### 把畫面描述量化，然後發現多幀 prompt 一直在丟掉自己買到的東西

使用者要求畫面分析更精細——目前寫「人在產線工作」，要能寫到「人在產線搬箱子」；並且假設影片沒有任何聲音，只靠影像判讀。

**先量再改**。畫面描述原本跟文件整理一樣完全沒有量化方式，所以先做 `scripts/measure_description_quality.py`（純讀資料庫、零 API 成本），把「現在有多糟」釘成數字：全庫 1,354 個描述 **73.6% 含籠統詞**、只有 **6.0% 含具體動作動詞**，平均 52.4 字。**產線類影片是最糟的一群**（PCB 工廠 94.7%、技嘉 93.9%、Intel 93.5%、BMW 92.3%），正好是使用者關心的類型。baseline 存成 `docs/eval-runs/desc-20260831_130730.json`。

**量的過程撞到一個沒預期的東西**：多幀片段有 **61.0%** 的描述在講「第一張／第二張／逐漸變化」，單幀只有 **0.6%**。追下去是 `_MULTI_FRAME_PROMPT_TEMPLATE` 那句「如果不同畫面之間內容有變化，簡短點出變化」——多幀本來是為了給模型時間維度、讓它講得出動作，付了 1.9 倍費用，然後被 prompt 換成「兩張圖不太一樣」。v32（組裝 SOP）10 段全是多幀，10 段全是元描述，沒有一句講出裝了什麼。

**規劃時把這件事排成獨立一步，實測證明那個規劃是錯的。** 原本的想法是「先只移除舊指令（P1），再單獨加具體動詞要求（P2）」，維持單變數。實跑候選 A（只移除）：元描述確實清到 3.8%，但描述縮短 26%、籠統率反升到 90%、具體動作腰斬——「點出變化」雖然導錯方向，至少逼模型去看細節，拿掉而不補，模型就直接縮短輸出。**移除舊指令與給新任務必須同一步做。**

**第二個候選指標全面勝出，卻是靠幻覺換來的。** 候選 B（移除＋要求「講出誰、對什麼、做了什麼」）具體動作率 16.2%→47.5%、元描述 57.5%→7.5%，三個代理指標都漂亮。人眼一看才發現：v32 是**純 3D 動畫、畫面裡沒有任何真人**，B 卻在 **10/10 段**寫出「作業員」「技術人員」，還編出「用手擰緊固定螺絲」。根因是句型本身——「誰、對什麼、做了什麼」預設畫面有施動者，沒人的時候模型就發明一個。

這一條值得單獨記：**代理指標擋得住退步，擋不住幻覺**。當初寫量測腳本時就在 docstring 裡註明「指標好轉不代表描述真的變好，仍然要人眼抽看」，這次是那句話第一次真的兌現。

**候選 C 加上護欄後收斂**（照 `pipeline/document.py` 既有的防幻覺寫法：只寫真的看得到的、沒有人就不要寫人、看到 3D 模型就說是模型、寧可少寫不要補完）：

| | 具體動作 | 元描述 | v32 提到人物（正確值 0%） |
|---|---:|---:|---:|
| 現行 | 16.2% | 57.5% | 0% |
| 候選 B | **47.5%** | 7.5% | **100%** ❌ |
| 候選 C ✅ | 31.2% | 7.5% | **0%** |

v34（真的有人）那一側，候選 C 的具體動作率從 14.3% 拉到 **35.7%**、元描述從 52.9% 降到 **4.3%**。

**雜訊校準**：同一個 prompt 在三輪實驗裡各跑一次，籠統率範圍 5pt、具體動作 7.6pt、元描述 11.3pt。候選 C 的 +21.4pt 與 −48.6pt 都遠超這個範圍，v32 的人物提及率 0%→100%→0% 更是無可爭議。**這也是為什麼對照組必須跟候選同一輪執行**，拿資料庫既有描述來比會把模型隨機性混進去。

**驗收**：426 個既有測試全過。實驗總花費 US$0.62（三輪、唯讀不寫庫），原始輸出在 `docs/eval-runs/desc-exp-multiframe-*.json`。

**沒做、也講清楚**：單幀 `_PROMPT` 完全沒動，而單幀是多數（有記錄幀數的 948 段裡佔 69%），全庫 73.6% 的籠統率主要來自它。只在 v32／v34 兩支驗證過，而且**兩支都不是真人產線影片**——使用者的目標情境（v4／v28／v33）還沒測。既有影片也還沒重新分析，資料庫裡仍是舊 prompt 的描述。

### 單幀 prompt：問姿勢不要問動作，以及一個「改字改到頂了」的結論

多幀那輪改完後接著處理單幀 `_PROMPT`——單幀是多數（有記錄幀數的 948 段裡佔 69%），全庫 73.6% 的籠統率主要來自它。測試集這次換成真人產線影片：**v28 Intel**（字幕只有 15%，最接近使用者說的「無聲影片只靠影像判讀」）、**v33 PCB 工廠**，外加 **v32**（純 3D 動畫、沒有真人）當幻覺對照組。三支都不在 `golden-set.csv` 裡（它只引用 video 1／2／3／4），重跑零副作用。

**這輪比的是兩種設計，不是一種**。單幀跟多幀的差別不只是張數——一張靜止畫面在物理上看不出動作的方向，一個人彎腰、雙手扶在紙箱兩側，可能是搬起、放下或只是扶著。所以候選 S1 是把多幀那套「動詞要具體到能重現」原封不動搬過來，候選 S2 則是承認這個限制、改要求描述「看得到的姿勢與接觸關係」，明講不要猜意圖。

| arm（90 段） | 長度 | 具體動作 | 姿勢接觸 | v32 提到人物 |
|---|---:|---:|---:|---:|
| 現行 | 52.2 | 4.4% | 14.4% | 0% |
| 候選 S1 | 69.4 | 6.7% | 17.8% | 0% |
| **候選 S2** ✅ | 74.8 | **11.1%** | **25.6%** | 0% |

**S1 幾乎沒有效果**（比現行只多 2.3pt，在雜訊內），只是把描述寫長——逼模型對單張靜止畫面講出動作動詞，它給不出比原本多的東西。S2 在 v28 那支的姿勢接觸率是 22.5% → 45.0%。三個 arm 在 v32 的人物提及率都是 0%，多幀那輪加的幻覺護欄移植過來仍然有效。

**誠實記兩件事**：
1. **S2 對「具體動作」的 +6.7pt 落在雜訊範圍內**（±7.6pt）。真正站得住的是 S1 與 S2 之間的差距——兩者同輪執行、都是新 prompt，唯一變數是動作那一段的框架。
2. **籠統率完全沒動**（93.3% → 94.4%），但那部分是指標自己的問題：詞表裡的 `設備`／`顯示`／`機器` 對半導體廠影片是正確用詞，一句同時講出「壓力計」與「設備」也會被標記。**這個指標對工廠類影片偏嚴，不適合單獨當驗收條件。**

**這輪最重要的結論不是 prompt**：多幀 prompt 改對拿到 +21.4pt，單幀 prompt 怎麼改都只有個位數。**單幀片段的瓶頸是那張畫面本身。** 想讓它再細下去，該投資的是「多給幾張畫面」——無聲影片跳過 ASR 把預算換成多幀（ASR 佔總成本 62～66%）、多幀觸發條件從「場景切分漏切」擴大到一般情況——不是繼續改字。

**驗收**：426 個既有測試全過。兩輪實驗合計 US$0.77（唯讀不寫庫），原始輸出在 `docs/eval-runs/desc-exp-*.json`。

**已知副作用**：描述平均長 43%，`segments.content` 是 generated column、BM25 會做長度正規化，重新分析過的影片跟舊影片的搜尋分數分佈會不一致——沒有實測過影響多大。既有影片也還沒重新分析，庫裡現在是新舊描述混在一起。

### 純畫面影片：跳過 ASR，把省下的錢換成畫面

上一節的結論是「單幀片段的瓶頸是那張畫面本身，不是 prompt」。要再細下去只能多給畫面，而錢從哪來——量成本組成時看到 **Whisper 佔一支影片總成本的 62～66%**（18.6 分鐘的 Intel 那支：US$0.1711 裡 ASR 就佔 US$0.1116）。它按分鐘計價、跟畫面複雜度無關，對沒有人說話的影片，這筆錢買到的只有幻覺。

**做成兩個獨立機制**，因為那是兩種不同的情況：沒有音軌的影片用 ffprobe 直接偵測、整段跳過 ASR；有音軌但字幕整欄是幻覺的（工廠環境噪音那種）ASR 已經花掉了省不掉，但一樣改成三幀取樣。

**判斷點放在轉錄之後、Phase B 之前**是關鍵。轉錄跟場景切分本來就是平行跑的，結果在畫面分析開始前就拿得到，所以「畫面是不是唯一的訊號來源」可以用**實際的轉錄結果**判斷，而不是只看有沒有音軌——實測整欄幻覺的那幾支音軌都正常，只看音軌完全抓不到。

**寫測試的時候測出一個 bug**：`is_transcript_column_junk()` 有樣本數下限 8 句（3 句裡重複 2 句就湊得出 67%，那是雜訊），所以空清單回 `False`。而真無聲影片的轉錄結果**正是空的**——只委派給它的話，最該加密取樣的影片反而拿不到多幀，跟本意完全相反。`_is_visual_only()` 因此自己先判一次「完全沒有字幕」。

**全庫掃描 23 支，5 支觸發，分辨力正確**：三支工廠影片全中（v4 BMW 72.2%、v28 Intel 75.0%、v8 Intel 64.8%），而 v33 PCB 工廠（6.1%）與 v31 技嘉（3.1%）正確地不觸發——那兩支有真人中文旁白，字幕是有用的。

**實跑 v28 完整重新分析驗證**（事前備份到 scratchpad）：

| | 長度 | 具體動作 | 姿勢接觸 |
|---|---:|---:|---:|
| 舊 | 53.5 | 5.6% | 29.9% |
| 新 | 83.3 | **16.8%** | **43.9%** |

107 個片段全部拿到三幀，花費 US$0.1727 → **US$0.2663（+54%）**，耗時 419 秒。描述終於寫得出可重現的動作——「一個白色的貨物箱由上方的吊運系統移動，沿著橫梁移動至另一個位置」，這正是使用者一開始說的「人在產線搬箱子」那個層級。

**這一輪要修正先前的一個說法**：規劃時說這個改動「成本持平」，實跑證明只有**沒有音軌**那條成立。v28 有音軌（工廠噪音），Whisper 還是得跑完才知道輸出是垃圾，所以是淨漲 54%。仍在使用者拍板的 2～3 倍範圍內，但不該講成持平。

**順帶得到一個偵測穩定性的證據**：這次 Whisper 對 v28 產生的幻覺跟上次**完全不同**（舊的 `... ... ...` 佔 65%，新的 `Tucson Water Treatment Plant` 佔 47.9%、含變體 88%），兩次都被同一個判斷抓到。**幻覺的內容會變，「一句佔滿整欄」這個型態不變。**

**跑的過程冒出一個新問題並修掉**：三幀 × `VLM_BATCH_SIZE=3` ＝ 同一批送出 9 張圖，**429 撞了 5 次**（靠既有重試救回來，107 個場景全數完成、0 失敗）。條件式多幀上線時驗證過的是每批最多 6 張圖、0 次撞限。新增 `VISUAL_ONLY_VLM_BATCH_SIZE = 2` 讓純畫面影片回到每批 6 張——**撞 rate limit 的是圖片張數不是場景數**，批次要跟著幀數走。

**驗收**：443 個測試通過（新增 17 支：音軌偵測三支、字幕整欄判斷五支、`_is_visual_only` 四支、幀數決策兩支、跳過 ASR 一支、三幀往下傳一支、批次縮小一支）。有一支既有測試轉紅而且轉得對——它傳空的轉錄結果進 `_run_vlm_phase()`，那現在代表「純畫面影片」，改成給真實字幕才測得到原本要測的兩幀觸發。

**沒做、也講清楚**：「有音軌但整欄幻覺」那條省不到 ASR 的錢，要在呼叫 Whisper 前就知道「沒有人說話」需要本地 VAD 模型，是新依賴、還沒評估（本地 CV 模型在這台機器上很慢有前例）。三幀的位置 20%／50%／80% 沒有掃過其他組合。其餘 4 支觸發的影片（v4／v5／v6／v8）沒有重新分析。

### 真正沒有音軌的影片：把測試素材自己造出來

P3 有兩條路徑，v28 只驗證了「有音軌但字幕整欄幻覺」那條。**沒有音軌**那條——也就是使用者原始需求裡明講的情境——只有單元測試蓋到，而且它跟另一條走的程式碼不同（`media.has_audio_stream()` 才是入口，會整段跳過 Whisper）。

**不用等真實素材**：用 `ffmpeg -c copy -an` 從 v33（走進工廠：PCB 線路板）剝掉音軌，內容完全真實，走既有的上傳登錄路徑進來成為 v36。同一支影片的有聲版就是天然對照組。

| | 長度 | 具體動作 | 姿勢接觸 | 幀數 |
|---|---:|---:|---:|---|
| v33 有音軌（舊 prompt／單幀） | 51.9 | 5.3% | 17.3% | `{1: 72, 2: 3}` |
| v36 無音軌（新 prompt／三幀） | 79.1 | **38.7%** | 37.3% | `{3: 75}` |

**成本 US$0.1181 → US$0.1072，−9.2%**。ASR 省下 US$0.0765（原成本的 65%），VLM 那部分漲成 2.58 倍。規劃時說的「成本不升反降」到這裡才算真的被驗證——v28 那次是淨漲 54%，因為它有音軌、Whisper 省不掉。具體動作率 7.3 倍是目前所有實驗裡最大的改善幅度，但那個對照同時變動了 prompt 與幀數，分不出各佔多少。

**中途誤判了一次**：非空的 `ocr_text` 從 57/75 掉到 27/75，第一眼看成退步。查下去發現 v33 那 57 個裡有 **43 個是字面字串 `"null"`**——正是 `docs/05` 早就記著的既有資料 bug。真正有文字的片段其實是 14 → 21、字元總量 156 → 353（**+126%**），佔位字串 43 → 6。新 prompt 的「寧可少寫也不要補完」意外連帶減輕了那個舊 bug。**覆蓋率這個指標本身會被髒資料灌水，看數字之前要先看內容。**

**留下一個沒處理的問題**：「不要描述畫面之間的差異」這條指令**隨幀數增加而變弱**。兩幀驗證時 v34 只剩 4.3%，三幀實測是 v28 16.8%、v36 28.0%（改之前的兩幀是 61.0%）。v36 出現「在第二張畫面中…在第三張畫面中」。仍遠好於改之前，但趨勢很清楚，之後要加幀數的話得先解決它。

### 三個假設全錯，但問對了問題：三幀的元描述不是缺陷

上一節把「三幀的元描述率比兩幀高」列成 P4 的前置條件。查完之後**決定不改，並把它降級**。

**假設一：開場那句在誘導逐幀敘述。** 現行 prompt 第一句是「以下 {n} 張畫面…依時間順序排列」，「N 張」「排列」本身就在暗示要逐張講。改成「依時間先後取到的幾個瞬間」、不點數量（候選 T1）。

**假設二：禁令位置太前面被稀釋。** 它夾在中間，後面還有 on_screen_text 一整段。改成硬規則並移到 description 那條的最後（候選 T2）。

**兩個都失敗**（v28＋v36＋v32 共 50 段，US$0.21）：元描述率 現行 20.0% → T1 16.0%／T2 22.0%，都在 ±11.3pt 雜訊內，而且 v32（3D 動畫）在 T1 下反而從 10% 升到 30%，方向相反。

**假設三也錯了。** 看樣本時注意到「**接著**，一個透明的電子元件被雙手握住」被算成元描述，但那是正當的時序敘述——三幀本來就會產生更多時序連接詞，我一度以為是指標在誤判。換成只抓「真的指涉圖片」的詞表重算，aggregate 幾乎一樣（20.0% → 22.0%）：舊詞表的偽陽性與漏抓大致抵銷。**指標沒有錯。**

**真正的收穫是這條問題的性質變了。** 三幀殘留的元描述跟 v32 當初那種**完全不是同一回事**——當初是「部件位置略有變化」，只講畫面在變、沒有任何內容；現在是：

> 畫面顯示一棟大型建築，標示為 Intel 的總部辦公大樓。**接著**，出現一位穿著藍色工作服且帶護目鏡的女性，她正在實驗室中從一個容器中取出物品。**最後**，女性將一個圓形器皿放置在實驗桌上。

內容完整，只是順帶提了一句畫面切換。而且 **48% 的描述含「接著／然後／最後」的時序敘述**，那正是花錢買多幀想要的東西——壓掉它反而會損失資訊。所以這條從「P4 的前置條件」降級成「已知的表面瑕疵」，**P4 解除阻塞**。

**順帶修掉實驗腳本的一個缺口**：它沒有 rate limit 重試，而正式流程有。這輪實測撞爆過一次——同一組畫面連跑 N 個 arm 等於把 token 用量乘上 arm 數（單次呼叫約 2,700 tokens、TPM 上限 200,000），整支腳本掛掉、已花的 US$0.18 作廢。現在比照 `analyzer._describe_segment_with_retry()` 補上重試。

**這一輪花了 US$0.39（含作廢的那次）換到一個「不要改」的結論。** 值得——n=1 的觀察會讓人以為 28% 是退步而急著修，實際上那 28% 裡多數是好描述。

### P4：把三層取樣收成一層，然後刪掉六樣東西

P2 的結論是「單幀片段的瓶頸是那張畫面本身」，所以要再細下去只能多給畫面。使用者拍板 `BUDGET_USD` 調到 **$1.50**、三幀位置取 **10%／40%／70%**。

**動手前先把帳算清楚**。用 v28／v33／v36 實跑反推的每片段費率（幾乎全部是 VLM 的圖片 token）：1 幀 $0.00056／段、3 幀 $0.00144／段，**倍率 2.57，兩支影片一致**。$1.50 之下，52 分鐘影片（ASR 的實際上限）餘裕 19～42%；60 分鐘那個理論最壞值只剩 7%，但它碰不到——Whisper 的 25MB 上限換算約 52～55 分鐘，超過會先卡在 ASR。

**最大的一筆是刪除，不是新增。** 統一成三幀之後，原本的三層取樣不再有分岔，`MULTI_FRAME_TRIGGER_SEC`／`MULTI_FRAME_FRACTIONS`／`VISUAL_ONLY_FRAME_FRACTIONS`／`VISUAL_ONLY_VLM_BATCH_SIZE`／`_frame_fractions_for()`／`_is_visual_only()` 全部移除，連同 12 支測試。那些是幾天前才寫的、有完整校準紀錄的程式碼——但校準紀錄留在文件裡就夠了，**留著不會被讀到的分支比少一個設定選項更糟**。`scene_detect.NormalizedScene.source_raw_duration` 保留但已無呼叫端，理由寫進它自己的 docstring：它是「這個場景是不是被機械式硬切出來的」唯一的紀錄，而且是之後要問「哪些內容值得抽超過三幀」時現成又已校準的訊號。

**`VLM_BATCH_SIZE` 3 → 2**：撞 rate limit 的是同一批送出的圖片張數不是場景數，三幀 × 批次 2 ＝ 每批 6 張。

**實跑兩支**：

| 影片 | 幀數變化 | 具體動作 | 姿勢接觸 | 元描述 | 成本 |
|---|---|---:|---:|---:|---:|
| v31 技嘉板卡工廠 | 1×21／2×12 → 全 3 | 9.1% → **30.3%** | 6.1% → **36.4%** | 18.2% → 12.1% | +31.7% |
| v29 線性代數 | 全 2 → 全 3 | 6.2% → 3.1% | 15.4% → 29.2% | 66.1% → **27.7%** | +18.5% |

v31 的 +21.2pt 遠超 ±7.6pt 雜訊。樣本差異直接：舊版「畫面展示一台機器運作的過程…**兩個畫面之間機器的運作狀態略有變化**」，新版「一台機器在進行印刷作業，**印刷頭沿著材料移動，材料下方有螺旋機制正運作**」。

**兩件沒做好、要講清楚的事**：

1. **v29 那組對照同時動了 prompt 與幀數**，所以我原本想回答的「靜態內容三幀是不是浪費」沒有乾淨的答案。它的具體動作率下降（6.2% → 3.1%）對講課影片來說可能是正確的（畫面上本來就沒有物理動作），籠統率大漲（43.1% → 92.3%）則是那個指標對長度敏感的已知問題。要真的答它，得在同一輪裡跑 2 幀與 3 幀、prompt 固定。
2. **批次 2 仍會撞 429**。v29 撞了 2 次（都靠重試救回、65 個場景 0 失敗）。我先前說「批次 2 回到條件式多幀驗證過的安全水位」**沒有完全成立**，只能說比批次 3 低（v28 那次是 5 次）。

## 2026-09-01：一份停在 05:15 的 SOP，追出兩個互相掩護的問題

起點是使用者的一句話：v37（手工製作巨大電機的過程，中國一家了不起的電機工廠，643 秒、62 個片段）的 SOP 文件，內容看起來全擠在影片開頭。追下去發現那底下有**兩個獨立的失效**，而且症狀長得一樣，所以一開始只看得到一個。

### 問題一：時間戳塌回前 32 秒，而 2026-08-30 說已經修好了

當時存的文件是 7 個步驟，`timestamp_sec` 全部落在 1.0～32.0。但把每一步的內容對回素材，**內容其實橫跨整支影片**：

| 文件寫的秒數 | 真正的片段 | 素材那一行 |
|---:|---:|---|
| 17.0 | 17 秒 | ✅ |
| 25.0 | 25 秒 | ✅ |
| 32.0 | **92 秒** | `[01:32｜92 秒]` 把線圈固定在定子內 |
| 10.0 | **310 秒** | `[05:10｜310 秒]` 定子浸入油漆 |
| 15.0 | **319 秒** | `[05:19｜319 秒]` 調整閥門 |
| 1.0 | **180 秒** | `[03:00｜180 秒]` 組裝電機、整理電纜 |
| 3.0 | **553 秒** | `[09:13｜553 秒]` 把鑽子和定子組裝到一起 |

「定子浸漆」是影片第 5 分鐘、「鑽子與定子組裝」是第 9 分鐘的內容——模型讀到了、也寫進文件了，只有 `timestamp_sec` 被填成 `MM:SS` 的秒數位。這正是 2026-08-30 那次追查的同一個 bug，當時的修法是素材同時給總秒數（`[03:18｜198 秒]`）。

**修法沒有失效，但也沒有根除。** 同一份素材、同一版程式重跑三次（$0.0035，不寫回資料庫）得到 12／10／15 個步驟，時間戳範圍 `17~603`、`0~629`、`0~629`——所以那份壞掉的文件是**單次抽樣**，不是程式壞了。但重跑的結果裡仍看得到殘留：run 3 出現 `10.0 定子浸入油漆`（真值 310＝`05:10`），run 2 出現 `1.0`（真值 60＝`01:00`，這次抄的是分鐘）。

`docs/05` 原本那條刪除線因此要降級：**從「已修正」改成「大幅改善、未根除，形態從整份塌陷變成逐步驟偶發」**。前端那道護欄擋不到這種——它只擋超出影片長度，而往前塌的時間戳全都在合法範圍內，點下去會正常播放，只是跳到錯的地方。

### 問題二：涵蓋率不是低，是極不穩定

使用者重整文件後拿到 17 個步驟、`00:17`～`05:15`，後五分鐘整片空白。這次時間戳大多對得上素材（17／25／34／…／222／235），所以不是問題一——**是模型自己決定寫到一半就停**。

而且不是沒東西可寫。05:15 之後還有 29 行素材，全是真實製程：`[07:34｜454 秒]` 切割機加工金屬管、`[08:56｜536 秒]` 轉子存放區、`[09:13｜553 秒]` 把鑽子和定子組裝到一起、`[10:03｜603 秒]` 檢修大型電機內部。分布也很偏：17 步裡有 **13 步落在前 131 秒**（前 20% 片長），幾乎一個片段一步，然後急速稀疏、停在 315。

拿現行 prompt 對「現行＋一條覆蓋規則」跑 3+3 次（$0.0102，不寫回資料庫）：

| | 涵蓋率（max/片長） | 步驟數 | 後半段步驟 | 時間戳對得上素材 |
|---|---|---:|---:|---|
| **A 現行** | **101.6% / 31.6% / 97.8%** | 12 / 18 / 10 | 1 / 0 / 3 | 11/12、16/18、9/10 |
| **B ＋覆蓋規則** | **95.6% / 97.8% / 97.8%** | 10 / 16 / 15 | 2 / 2 / 4 | 7/10、16/16、14/15 |

**A 的跨度是 70pt**，遠超 `docs/18` 記的任何雜訊帶。使用者看到的那份停在 05:15，就是 A run2 那種結果。加規則後跨度剩 2.2pt，而且**步驟數沒有被稀釋**（平均 13.3 → 13.7）、`uncovered` 也沒有被逼成空的。規則刻意保留「真的沒有就寫進 uncovered，不要為了填滿而發明步驟」這句護欄——`docs/18` §6.2 的教訓是代理指標擋得住退步、擋不住幻覺。

順帶抓到 A run1 寫出 653 秒，超過片長 643。同一個變異，另一個方向。

### 人眼抽看：覆蓋率修好了，內容對位沒有

## 2026-09-01（當天稍晚）：把那條規則真的上線，順便推翻自己前一段的結論

### 先做量測腳本，因為前一輪的數字是臨時查詢查出來的

`scripts/measure_document_coverage.py`，純讀 DB、不呼叫 API。五項指標：涵蓋率（兩個分母）、後半段步驟數、尾段 20% 步驟數、超出片長的步驟數、**對不上任何一行素材的步驟數**。

兩個過程中的發現：

1. **分母要用素材、不能只用片長**。素材本來就到不了片尾（差一個場景長度），拿片長當分母會系統性低估。全庫 15 支用片長算只有 2 支過 90%，用素材算是 6 支。
2. **第一版的防虛構指標是錯的**。原本寫成「時間戳有沒有落在某個片段的 `[start_sec, end_sec]` 區間內」，量出來全庫**恆為 0**——場景是從 0 連續鋪到片長的，中間沒有空隙，任何合法秒數都必然落在某個片段裡。改成「等不等於某一行素材的行首秒數」才有鑑別力（全庫 212 步有 22 步對不上，集中在 Intel 8/16、太極 5/20）。要抓的是「有沒有抄」，不是「在不在範圍內」。

改動前的基準線：`docs/eval-runs/doccov-20260901_172232.json`。

### 推翻一：「加了規則後跨度剩 2.2pt」是三次抽樣的運氣

平均 88.0%（對照舊 prompt 三次的 32.5%），但 **9/12 過 90%，仍有三次壞抽樣**。上一節的 B 組掉進了它自己在 A 組診斷出的同一個陷阱：**三次不足以描述一個變異這麼大的分布**。原訂通過條件「連跑三次都 > 90%」實際只有約四成機率達成。

### 推翻二：`temperature` 這條路看起來是答案，實際不是

這支呼叫從來沒設過 `temperature`，用的是預設 1.0。既然診斷是「變異」，最直接的槓桿就是它。v37 設 0 之後**連跑四次全部 100.0%、15 步、脫格 0，完全穩定**。

### 最後上線的：規則 + 補寫一次

prompt 的第四條規則負責「寫多遠」，程式層的 `_extend_to_the_end()` 負責「保證」——文件停在門檻（素材長度的九成）之前，就**只拿沒被寫過的那段素材**再問一次，補回來的接成新的一節，並且明確允許回空的 `steps`（尾段真的只剩片尾字卡時，那是正確答案）。

### 先量再做，而且量出來的東西改變了設計

三件事在寫任何功能程式碼之前就量完了（總花費 US$0.037），完整數字在 [`19-停格畫面問答功能計畫.md`](19-停格畫面問答功能計畫.md)：

1. **抽幀是逐格準確的**。`extract_frame()` 的 `-ss` 放在 `-i` 之前是快速 seek，所以要驗。同一支影片抽 409.0／409.4／409.8／410.5／412.0／414.0 得到六張不同的畫面，沒有吸附到關鍵幀——「使用者停在哪就問哪一格」這個前提成立。
2. **`detail=high` 貴 12.6 倍**（2,880 → 36,882 prompt tokens，US$0.00045 → US$0.00554）。一題 high 比產一整份 SOP 還貴。
3. **計數型問題兩級都不可靠**。一張約 10 名球員＋滿場觀眾的籃球場全景，low 答「四個人」、high 答「五個人」。**加錢解決不了。** 辨識型問題（有什麼／在做什麼／寫了什麼）在 low 就答得好。

使用者舉的三個例子裡有兩個是計數型。這件事寫在計畫的最前面，不是等做完才發現。

### 踩到的雷：防幻覺的話不能跨情境共用

第一版探針的 prompt 抄了文件產生器那套「看不出來就說看不出來，不要推測」，結果**六題全部回「看不出來。」**，包括那張一望即知的籃球場全景。

**在「整理文件」裡寧可少寫，在「使用者問了一個問題」裡少寫就等於功能壞掉。** `frame_qa.py` 的 prompt 因此只保留「不要編」這一句，並有一個測試釘住它，防止之後有人「順手加強防幻覺」。

### 做出來的

後端 `pipeline/frame_qa.py` ＋ `video_service.answer_about_frame()` ＋ `POST /videos/{id}/frame-qa`（掛在 videos 底下、不碰對話狀態）；前端 `VideoPlayer` 加 `onTimeChange`、`ChatBubble` 加 `frameLabel`、`ConversationPage` 加畫面模式。設計取捨見 [`02-technical-decisions.md`](02-technical-decisions.md)。

### 順手修掉一個既有 bug

第一次實跑時畫面顯示的錯誤是 `Cannot read properties of undefined (reading 'message')`。真正原因是上面那個 404——FastAPI 回自己的 `{"detail": "Not Found"}`，而 `client.ts` 的 `request()` 直接讀 `body.error.message`，**在錯誤處理裡又丟一個 TypeError，把真正的錯誤蓋掉**。這是所有 API 呼叫共用的路徑，跟這個功能無關，只是這次剛好踩到。

## 2026-09-02（下午）：AI對話搜完先定格

使用者要求 AI對話的結果呈現跟片段搜尋一致：**搜完自動帶出第一名，但畫面停在那一格、不要直接播放**。

這是 §8.9 沒做完的一半。那次（2026-08-26）給搜尋頁加了「自動選第一名、不自動播放」，紀錄裡明寫「對話搜尋頁沒傳這個 prop」——`VideoPlayer.autoPlay` 預設 `true`，所以對話頁一直是「不自動選、點了就播」。現在兩頁共用同一份規則：程式自動帶出來的選取不播，使用者自己點結果才播。

**順帶讓停格問答更好按**：`autoPlay={false}` 時播放器仍然 seek 到片段起點、只是不 play，`onSeeked` 照樣回報秒數，所以「問這一格（MM:SS）」一開始就顯示正確時間。原本要先讓它播、再暫停才問得到那一格。

**已知取捨**：「播放第二段」這種 `select_result` 走同一條 `onSuccess`，所以連它也只會定格。要讓這一種例外自動播，後端得多回一個 action 欄位（`reply_text` 是自然語言，不能拿來判斷）。
