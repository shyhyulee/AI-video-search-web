# 停格畫面問答功能計畫（已完成）

> **類型**：執行紀錄｜**狀態**：已實作並實跑驗證（2026-09-01）
> 分類說明與完整索引見 [`../README.md`](../README.md)。

## 1. 文件目的

記錄「對停在某個時間點的畫面提問」這個功能的需求、動手前的可行性實測、拍板的決定與實作結果。

**第 1～5 節寫在開發之前**（含第 4 節那些決定了設計的實測數字），第 6 節是實作計畫，**第 9 節是做完之後補的驗證結果**。這個順序是刻意保留的：先量再做、量到什麼就照什麼設計，事後不回頭修飾當初的判斷。

## 2. 原始需求

使用者要求（2026-09-01）：

> 在對話搜尋的頁籤增加一個功能。當使用者選擇播放某個影片後，然後將影片停留在某個時間點。這個時候在對話框裡可以針對這張停格的影片，也就是照片。針對照片內容進行即時的分析問答。
> EX: 畫面中有幾個人?畫面中有幾個箱子? 出現的食物有哪些?

跟現有的搜尋不同：搜尋是「在整個影片庫裡找片段」，這個是「就這一格畫面，回答我的問題」——不查索引、不比對 embedding，直接把那張圖交給 VLM。

## 3. 現況盤點：可以直接重用的東西

| 需要什麼 | 現況 | 結論 |
|---|---|---|
| 播放器是什麼 | 對話頁用本地 `<video>`，`src` 是 `/api/v1/videos/{id}/stream`（`VideoPlayer.tsx`） | **不是 YouTube iframe**，可以在後端取得同一支檔案 |
| 影片檔在不在 | 31 支影片 `file_path` 全部非 NULL，檔案都在 `video/` | 每一支都能抽幀 |
| 抽幀工具 | `pipeline/frames.py:extract_frame()` 已存在（VLM 與本地 OCR 共用） | 直接用，不必新寫 |
| 送圖給模型 | `pipeline/vlm.py:describe_segment()` 已有 base64＋`image_url` 的完整寫法 | 照抄同一套 |
| 失敗處理 | `services/video_service.py:generate_thumbnail()` 已有「ffmpeg 失敗就回 None」的既有寫法 | 照同一個模式 |

**唯一缺的前端能力**：`VideoPlayer` 目前沒有把 `currentTime` 暴露給呼叫端，拿不到「使用者現在停在第幾秒」。

## 4. 動手前的實測（總花費 US$0.037）

### 4.1 抽幀是不是逐格準確？

這是整個功能的地基：使用者停在 409.4 秒，抽出來的必須是那一格，不能是最近的關鍵幀。`extract_frame()` 的 `-ss` 放在 `-i` 之前（快速 seek），所以要驗。

同一支影片抽六個相近時間點，比對 md5：

| 時間點 | md5（前 10 碼） | 檔案大小 |
|---:|---|---:|
| 409.0 | `be4e079856` | 80,562 |
| 409.4 | `aad42e3668` | 79,839 |
| 409.8 | `e2c0978878` | 70,322 |
| 410.5 | `d35c39e8de` | 68,605 |
| 412.0 | `3d25e00aef` | 70,728 |
| 414.0 | `f0d0cb5b2d` | 144,774 |

**六張全都不同 → seek 是準確的，沒有吸附到關鍵幀。地基成立。**

（過程中一度以為抓到 bug：v3 的片段 `398.8~409.5` 描述寫「一名紅衣球員準備投籃、兩名白衣防守」，但 409.0 抽出來是教練特寫。查下去是正常的——VLM 取樣在片段的 0.2/0.5/0.8，也就是 400.9／404.2／407.4，而 409.0 是那段的最後一刻，鏡頭已經切走。**片段描述不等於片段內每一格**，這件事對這個功能反而是重點：使用者問的是「這一格」，答案只能來自這一格。）

### 4.2 成本：`detail` 該用哪一級

gpt-4o-mini，1280×720 的畫面：

| `detail` | prompt tokens | 每題成本 |
|---|---:|---:|
| `low` | 2,880 | **US$0.00045** |
| `high` | 36,882 | **US$0.00554**（12.6 倍） |

對照：一次對話搜尋約 US$0.0002、整理一份文件 US$0.0038。**一題 `high` 的畫面問答比產一整份 SOP 還貴。**

### 4.3 準確度：三張真實畫面，人眼對過原圖

| 畫面 | 問題 | 真值 | `low` | `high` |
|---|---|---|---|---|
| BMW 工廠（一台人形機器人） | 有幾個人？ | 0 個真人 | 「一台人形機器人，沒有其他人」✅ | 同左 ✅ |
| NBA 球場全景 | 有幾個人？ | 場上約 10 名球員＋1 裁判＋滿場觀眾 | 「四個人」❌ | 「五個人，還有許多觀眾」❌ |
| 電機工廠手部特寫 | 有幾個人？ | 手/手臂 1 人，背景另有腿部 | 「只看到一隻手」⚠️ 漏掉背景的人 | 「僅顯示一隻手，可能只有一個人」⚠️ |
| NBA 球場全景 | 有哪些東西？場地是什麼？ | 球員、籃框、籃球場、觀眾席 | 「球員、籃框，場地是籃球場」✅ | — |
| 電機工廠手部特寫 | 人在做什麼？拿什麼？ | 手握紅色電線束 | 「用手握住一根紅色的電線」✅（多讀了「工具」） | — |
| BMW 工廠 | 畫面上寫了什麼字？ | 大字幕＋`FRAME` 浮水印＋德文指示牌 | 逐字讀出大字幕 ✅（漏掉小的德文牌） | — |

**兩個結論：**

1. **辨識型問題（有什麼／在做什麼／寫了什麼）在 `low` 就好用**，每題 US$0.00045。
2. **計數型問題兩級都不可靠**，而且 `high` 多花 12.6 倍換來的是「四個」變「五個」——真值是 10 以上。**加錢解決不了這件事。**

使用者舉的三個例子裡，「有幾個人」「有幾個箱子」屬於第 2 類，「出現的食物有哪些」屬於第 1 類。

### 4.4 踩到的雷：防幻覺的話不能照抄文件產生器那套

第一版探針的 prompt 寫了「請只根據畫面回答，看不出來就說看不出來，不要推測」——文件產生器就是靠這種句子壓幻覺的。結果**六題全部回「看不出來。」**，包括那張一望即知的籃球場全景。

在「整理文件」裡寧可少寫，在「使用者問了一個問題」裡少寫就等於功能壞掉。**這兩個情境的護欄不能共用。**

## 5. 拍板的決定

| 決定 | 選擇 | 理由 |
|---|---|---|
| 畫面從哪來 | **後端 ffmpeg**（`extract_frame`） | 前端 canvas 擷取受瀏覽器解碼差異影響，而且後端已經有現成、實測準確的工具；前端只要送 `video_id` ＋ `at_sec` |
| `detail` 等級 | **`low`** | 見 4.2／4.3：`high` 貴 12.6 倍且沒換到正確答案 |
| 怎麼區分「問畫面」與「新搜尋」 | **明確模式（按鈕）**，不交給 intent LLM | 自動判斷要多一次分類呼叫，而且 `docs/04` 已記過現有 intent 會改寫使用者原句（否定詞消失那個 bug）。誤把「畫面中有幾個人」判成新搜尋，使用者只會看到一堆不相干片段 |
| 計數不準怎麼辦 | **不特別處理，模型答什麼就顯示什麼**（使用者決定） | 不加數量護欄、不加免責文案。代價是「四個人」那種看起來很肯定的錯答會照樣出現，列為已知限制 |
| 能不能追問 | **同一格可追問**（使用者決定） | 「那箱子呢？」要有意義。上下文放前端，時間點一變就清空 |
| 這一版範圍 | **只做對話搜尋頁**（使用者決定） | 後端端點設計成不綁對話，之後推到搜尋頁／影片庫不用重寫 |
| 要不要進 `ConversationState` | **不進** | 那份狀態是搜尋語意（`active_query`／`last_results`／`selected_result`）。畫面問答不產生結果，也不該影響下一輪搜尋的指代解析 |
| 成本記在哪 | **這一版只回傳給前端顯示，不寫資料庫** | 不新增欄位或表；要記帳另議 |

## 7. 刻意不做

- **多格比較**（「這兩格差在哪」）——`vlm.py` 的多幀 prompt 已知會產生「元描述」（只講畫面在變、不講內容），見 [`../09-畫面分析精細化計畫.md`](../09-畫面分析精細化計畫.md) §6.6
- **整支影片問答**——那是搜尋要做的事
- **把答案寫回資料庫或搜尋索引**——不可靠的計數會污染索引
- **YouTube 搜尋頁的 iframe 畫面**——跨來源拿不到影格，而且那頁的影片還沒下載

## 8. 已知限制與風險（開發前就知道的）

- **計數會給出自信但錯誤的答案**，這是實測結果不是推測（4.3）。依使用者決定不做特別處理。
- **沒有量化評測方式**，跟文件整理一樣只能人眼看。第 4 節的三張畫面是舉例，不是樣本。
- **答案只依據那一格**，不看前後文、不看字幕、不看片段描述。使用者問「他剛剛在做什麼」會答不出來——這是設計，不是 bug。
- **每題都花錢**（US$0.00045）。跟搜尋一樣是使用者主動送出才觸發，但沒有次數上限。
- **`low` 讀不到小字**：實測漏掉畫面角落的德文指示牌。文字類問題可能需要 `high`，這一版不做自動升級。


## 9. 實作結果（2026-09-01）

### 9.1 實際做出來的東西

後端 `pipeline/frame_qa.py`（新檔）＋ `video_service.answer_about_frame()` ＋ `POST /videos/{id}/frame-qa`，前端 `VideoPlayer` 加 `onTimeChange`、`ChatBubble` 加 `frameLabel`、`ConversationPage` 加畫面模式。全部照第 6 節，沒有偏離。

**多做的一件事**：`FrameUnavailableError` 對映成 **422** 而不是 404——影片存在（404 已經由 `VideoNotFoundError` 表達過了），是「這一秒抽不出畫面」，使用者送出的請求本身沒辦法被滿足。

### 9.2 順手修掉一個既有的前端 bug

驗證時第一次跑，畫面上出現的錯誤訊息是 `Cannot read properties of undefined (reading 'message')`。真正的原因是**後端還沒重啟、少了新路由**，FastAPI 回的是它自己的 `{"detail": "Not Found"}` 而不是 `api/errors.py` 那個 Error Schema；`client.ts` 的 `request()` 直接讀 `body.error.message`，於是**在錯誤處理裡再丟一個 TypeError**，把真正的錯誤蓋掉。

這跟這個功能無關，是所有 API 呼叫共用的路徑，**只是這次剛好踩到**。修法是格式不符就退回 `HTTP {status}` 的通用訊息。

### 9.3 實跑驗證

**後端**（另起一支 uvicorn 在 8001，不動使用者自己那支）：

| 情境 | 結果 |
|---|---|
| 辨識型（BMW 影片 300 秒，「畫面中出現了哪些東西？」） | 「出現了一個機器人，它在一面灰色的牆壁旁邊。牆上有一條白色的橫幅，上面顯示了一些文字。」✅ 對得上原圖 |
| 追問（帶 1 輪 history，「那它是真人嗎？」） | 「畫面中出現的機器人並不是真人，它是一個機械裝置。」✅ 有吃到上下文 |
| 影片不存在 | 404 `VIDEO_NOT_FOUND` |
| 拖到片長之外（99999 秒） | 422 `FRAME_UNAVAILABLE`，訊息講得出是哪一秒 |
| 單題成本 | **US$0.00046**，跟 §4.2 量的 US$0.00045 一致 |

**前端**（Playwright 實跑，把 frame-qa 導到 8001）：

| 檢查 | 結果 |
|---|---|
| 按鈕顯示目前時間 | `問這一格（04:12）` |
| 畫面模式列 | `針對畫面 04:12 提問` ＋ 影片標題 ＋ 取消 |
| 泡泡標記 | 問與答兩則都標 `畫面 04:12` |
| 狀態列 | `花費 $0.0005｜問的是 04:12 的畫面` |
| 追問帶上下文 | 第三題的請求 `at_sec=252`、`history` 2 輪，`history[0].question` 正確 |
| **時間點一變就清空** | 拖到 300 秒後再問，`at_sec=300`、`history` **0 輪** ✅ |
| console error | 零 |

`tsc -b --noEmit`／`oxlint`／`npm run build` 全過；後端 463 個測試通過（新增 13 個）。

### 9.4 沒有解決的（跟第 8 節一致，實作後仍然成立）

- **計數仍然不可靠**，依使用者決定不做特別處理。
- **沒有量化評測**，只有人眼抽看。
- **成本沒有記進資料庫**，只回傳給前端顯示。
- **`low` 讀不到小字**，文字類問題可能需要 `high`，這一版不做自動升級。
